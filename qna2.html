1. 클로저란? 응용 사례와 메모리 누수
76341025594893716417652661907333149689

질문 — 클로저가 뭔가요? 그리고 클로저가 메모리 누수를 일으키는지, 클로저 안의 this는 어떻게 되는지, 실무에서 실제로 쓴 사례를 바로 쓸 수 있는 코드로 보여 주세요.

지원자 답변 — "함수 안에 함수를 중첩해서, 내부 함수가 외부 함수의 변수에 접근하는 게 클로저입니다." → 정의만 외운 수준. 메모리·this·실무 사례에서 막힘.

정답

  1. 정의 — 변수가 아니라 스코프를 붙잡는 것. 함수가 생성될 때 자신이 정의된 렉시컬 환경(스코프 체인)에 대한 참조를 함께 가집니다. 외부 함수가 반환된 뒤에도 내부 함수가 그 환경을 참조하고 있으면 환경은 해제되지 않습니다. "외부 함수 실행이 끝났는데 변수가 살아 있다"는 현상은 결과이고, 원인은 스코프 체인 참조입니다.

  2. 메모리 누수는 자동이 아니다. 클로저 자체는 누수가 아니라 의도된 참조 유지입니다. 누수가 되는 건 "더 이상 필요 없는데도 참조가 남는" 경우뿐입니다.

    • setInterval 콜백이 큰 객체를 캡처한 채 clearInterval이 안 됨
    • addEventListener 핸들러가 DOM 노드를 캡처한 채 removeEventListener가 안 됨
    • 전역 변수/모듈 스코프 캐시가 클로저를 영구 보관
    • 대응: 생명주기에 맞춰 해제, 키가 객체면 WeakMap/WeakRef 사용

  3. this는 클로저에 캡처되지 않는다. this는 스코프 변수가 아니라 호출 방식으로 결정되는 바인딩입니다. 그래서 일반 함수는 호출 주체에 따라 this가 바뀌고, 화살표 함수는 자기 this가 없어 상위 스코프의 this를 렉시컬하게 가져옵니다. 클로저가 보존하는 건 var/let/const 변수이고, this·arguments는 별개 메커니즘입니다.

  4. 반복문 함정. for (var i = ...)는 i가 함수 스코프라 모든 콜백이 같은 변수 하나를 공유해 루프 종료값을 봅니다. let은 반복마다 새 바인딩을 만들어 각 콜백이 자기 값을 캡처합니다. 레거시 코드라면 IIFE로 값 복사.

  5. 실무 사례 — 면접관이 듣고 싶은 부분.

    • 디바운스/스로틀: 타이머 ID를 클로저에 숨겨 전역 오염 없이 호출 횟수 제한
    • 메모이제이션/커링: 계산 결과 캐시를 클로저에 보관
    • 모듈 패턴: 내부 상태를 비공개로 두고 조작 함수만 노출 (ES Module 이전의 표준 캡슐화)
    • React Hooks: useState/useEffect/useCallback은 렌더마다 만들어지는 클로저에 값을 가둡니다. 이게 stale closure 문제의 뿌리 (→ 3번 항목)
// 클로저로 타이머 ID를 캡슐화한 디바운스
function debounce(fn, wait) {
  let timer = null;                       // 외부에서 접근 불가
  return function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}
2. 이벤트 루프 — 마이크로/매크로태스크와 렌더링 순서
76374524970914287737641906744503524977

질문 — async/await, Promise, setTimeout의 실행 순서를 말하고, 이벤트 루프와 마이크로/매크로태스크 우선순위, 그리고 await이 "블로킹"한다는 말의 실제 의미를 설명하세요. 추가로 Promise.then과 queueMicrotask 중 어느 쪽이 먼저 실행되나요?

지원자 답변 — "마이크로태스크가 매크로태스크보다 먼저 실행됩니다." → 전체 순서와 await의 동작 원리에서 막힘.

정답

  1. 한 사이클의 순서. 동기 코드(현재 태스크) 실행 → 마이크로태스크 큐를 전부 비움(실행 중 추가된 마이크로태스크까지 모두) → 필요 시 렌더링(스타일 계산 → 레이아웃 → 페인트 → 합성) → 다음 매크로태스크 1개. 핵심은 "마이크로태스크는 하나씩이 아니라 큐가 빌 때까지" 돌고, 렌더링은 매 태스크마다 보장되는 게 아니라 브라우저가 프레임 주기(보통 ~60fps)에 맞춰 수행한다는 점입니다.

  2. await은 스레드를 멈추지 않는다. await은 해당 async 함수의 나머지 코드를 마이크로태스크로 등록하고 함수에서 빠져나옵니다. 호출한 쪽은 계속 진행합니다. 즉 "현재 async 함수의 후속 코드만 지연"되는 것이고, 메인 스레드는 블로킹되지 않습니다. await x는 대략 Promise.resolve(x).then(() => 나머지)와 같은 타이밍입니다.

  3. ⚠️ 영상 정정 — 마이크로태스크 사이의 "우선순위"는 없습니다. 영상은 queueMicrotask > Promise.then > MutationObserver 순으로 우선순위가 있다고 단정하는데, 사실이 아닙니다. 세 가지 모두 같은 마이크로태스크 큐에 FIFO로 들어갑니다. 순서를 결정하는 건 우선순위가 아니라 큐에 등록된 시점입니다.

    queueMicrotask(() => console.log('A'));
Promise.resolve().then(() => console.log('B'));
queueMicrotask(() => console.log('C'));
// A B C — 등록 순서대로. queueMicrotask가 "더 높아서" 먼저가 아님

    MutationObserver 콜백도 마이크로태스크지만, DOM 변경을 모아 배치로 전달하기 때문에 "늦게 보이는" 것이고 우선순위가 낮은 게 아닙니다.

  4. 프레임 관련 API의 위치. requestAnimationFrame 콜백은 마이크로태스크도 매크로태스크도 아니고, 렌더링 직전에 실행됩니다. requestIdleCallback은 프레임에 여유가 있을 때. 애니메이션은 setTimeout이 아니라 rAF를 써야 하는 이유입니다.

  5. 실무로 이어지는 지점.

    • 마이크로태스크를 과도하게 쌓으면 큐가 비기 전까지 렌더링이 밀려 화면이 멈춥니다 (마이크로태스크는 "렌더 전에 전부" 처리되므로)
    • try/catch는 같은 동기 실행 흐름만 잡습니다. await 없는 Promise 체인의 거부는 잡히지 않아 unhandledrejection으로 흘러갑니다
    • 무거운 계산은 태스크를 쪼개거나 Web Worker로 옮겨야 합니다

3. React 18 동시성 업데이트에서 클로저 함정
7632253913756345018

질문 — React 18의 동시성 업데이트는 왜 클로저 함정(stale closure)을 만드나요? 원리를 설명하고 해결책을 제시하세요.

지원자 답변 — 새 훅 이름은 나열했지만, 렌더 중단/재시작이라는 동시성의 핵심을 몰라 막힘.

정답

  1. 뿌리는 "렌더마다 새 클로저". 함수 컴포넌트는 렌더될 때마다 새로 실행되고, 그 안의 콜백은 그 시점의 state/props 값을 캡처합니다. 비동기 콜백(타이머, fetch 응답, 이벤트 핸들러)이 나중에 실행되면 이미 낡은 스냅샷을 보게 됩니다. 이건 React 18 전에도 있던 문제입니다.

  2. 동시성이 왜 이걸 악화시키나. React 18의 동시 렌더링에서 렌더는 중단·재개·폐기될 수 있습니다. 즉 한 번 시작한 렌더가 끝까지 간다는 보장이 없고, 더 높은 우선순위 업데이트가 끼어들면 작업 중이던 렌더가 버려지고 다시 시작됩니다. 결과적으로 "렌더 중에 외부 가변 값을 읽는" 코드는 같은 커밋 안에서도 서로 다른 값을 볼 수 있어, 이전에는 운 좋게 숨어 있던 stale closure/tearing이 드러납니다. 느린 네트워크나 렌더량이 많을 때 재현되는 이유입니다.

  3. 해결책 4가지.

    • 함수형 업데이터: setCount(c => c + 1) — 외부 클로저 값에 의존하지 않고 최신 state를 인자로 받습니다. 가장 먼저 적용할 기본값
    • useRef로 최신 값 보관: ref 객체는 렌더 간 동일 참조라 ref.current를 읽으면 항상 최신. 타이머·구독 콜백에서 유용
    • useSyncExternalStore: 외부 스토어를 동시성 안전하게 구독하는 공식 API. 전역 스토어를 직접 읽어 생기는 tearing을 막습니다. 상태 관리 라이브러리를 React 18에 맞출 때 쓰는 정석
    • 의존성 배열 정확히 쓰기: eslint-plugin-react-hooks의 exhaustive-deps를 경고가 아니라 에러로 운영. 의존성 누락이 stale closure의 가장 흔한 입구입니다

  4. 보너스 — useEffect 정리 함수. useEffect가 재실행될 때 이전 이펙트의 정리(cleanup)가 먼저 돌아야 낡은 구독/타이머가 남지 않습니다. React 18 StrictMode가 개발 모드에서 이펙트를 한 번 더 마운트/언마운트하는 건 바로 이 정리 누락을 드러내기 위한 장치입니다.

4. 자동 배칭과 useTransition 스케줄링 원리
7633486717328418929

질문 — React 18의 자동 배칭(automatic batching)의 경계, 우선순위, 중단 시점을 밑바닥 원리까지 설명하세요. startTransition 안의 상태 변경은 왜 인터랙션을 막지 않나요?

지원자 답변 — "자동 배칭, useTransition, 동시 렌더링" 이름은 유창하게 나열. 경계와 우선순위 모델에서 막힘.

정답

  1. 배칭의 경계가 달라진 게 핵심. React 17까지는 React 이벤트 핸들러 안에서만 여러 setState가 하나의 렌더로 합쳐졌습니다. Promise .then, setTimeout, 네이티브 이벤트 리스너 안에서는 합쳐지지 않아 setState 횟수만큼 렌더가 돌았습니다. React 18은 createRoot를 쓰면 이 모든 경계에서 자동으로 배칭합니다. 이게 "자동 배칭"이라는 이름의 실체입니다. 반대로 즉시 적용이 필요하면 flushSync로 명시적으로 빠져나옵니다.

  2. 우선순위는 Lane 모델. React는 업데이트마다 lane(비트마스크로 표현된 우선순위 집합)을 부여합니다. 사용자 입력 같은 discrete event는 높은 lane, transition은 낮은 lane입니다. 스케줄러는 높은 lane 작업을 먼저 처리하고, 렌더 도중 더 높은 lane이 들어오면 현재 작업을 중단하고 버리고 다시 시작합니다. Fiber 구조가 작업을 노드 단위로 쪼개 둔 덕분에 이 중단이 가능합니다.

  3. startTransition이 인터랙션을 막지 않는 이유. transition으로 표시된 업데이트는 낮은 우선순위 lane으로 들어갑니다. 그래서 그 업데이트의 렌더가 진행되는 중에 사용자가 타이핑하면, 타이핑 업데이트가 더 높은 lane이므로 transition 렌더를 중단시키고 먼저 처리됩니다. 사용자는 입력이 즉시 반영되는 걸 보고, 무거운 리스트 갱신은 뒤에 따라옵니다. useTransition의 isPending으로 로딩 표시를 걸 수 있습니다.

  4. 구분해서 말해야 하는 두 가지. useDeferredValue는 "값"을 뒤처지게 하고, useTransition은 "업데이트"를 낮은 우선순위로 표시합니다. 전자는 값을 받는 쪽에서, 후자는 값을 바꾸는 쪽에서 적용합니다.

  5. 주의. startTransition 안에서는 동기적으로 state를 바꿔야 효과가 있습니다. await 뒤에서 setState하면 transition 컨텍스트를 벗어납니다 (React 19의 startTransition은 async 함수를 지원하도록 개선되었습니다).

5. React 19 Server Components + Actions
7640055089062889381

질문 — React 19의 Server Components와 Actions 원리는 무엇인가요? useState 없이 폼 제출로 상태를 갱신할 수 있는 이유는? 기존 클라이언트 컴포넌트와의 본질적 차이는?

지원자 답변 — "서버 렌더링이라 JS가 줄고 성능이 좋다" 수준. 데이터가 폼에서 서버로 가서 UI가 자동 갱신되는 흐름을 설명하지 못함.

정답

  1. ⚠️ 영상 정정 — RSC는 "서버가 HTML을 만들어 교체"가 아닙니다. 영상은 "가상 DOM 없이 서버가 HTML을 직접 생성해 브라우저가 교체한다"고 설명하는데 부정확합니다. Server Components는 서버에서 렌더되어 **직렬화된 React 엘리먼트 트리(RSC Payload, Flight 포맷)**를 스트리밍합니다. 클라이언트 React는 이 페이로드를 받아 **기존 트리와 재조정(reconcile)**합니다. 그래서 갱신 시 폼 포커스나 클라이언트 컴포넌트의 로컬 state가 날아가지 않습니다. HTML 통째 교체라면 불가능한 동작입니다.

  2. Server Components의 실체.

    • 서버에서만 실행되고 클라이언트 번들에 포함되지 않습니다. 무거운 라이브러리(마크다운 파서, DB 클라이언트)를 써도 번들 크기에 영향이 없는 게 가장 큰 실익
    • DB·파일시스템에 직접 접근 가능. async 컴포넌트로 await 사용
    • state·이펙트·브라우저 API를 쓸 수 없습니다. 인터랙션이 필요하면 'use client' 경계를 만들어 클라이언트 컴포넌트로 분리
    • 기존 SSR과의 차이: SSR은 같은 컴포넌트를 서버에서 HTML로 그리고 클라이언트에서 다시 하이드레이션합니다. RSC는 애초에 클라이언트로 내려가지 않습니다

  3. Server Actions의 실체. 'use server'가 붙은 함수는 빌드 시 엔드포인트로 등록되고, 클라이언트에는 그 참조 ID만 남습니다. <form action={myAction}>으로 넘기면 제출 시 React가 그 ID로 POST를 보냅니다. 서버에서 함수가 실행되고, 데이터를 바꾼 뒤 영향받은 Server Component를 다시 렌더해 새 RSC 페이로드를 응답에 함께 실어 보냅니다. 클라이언트는 이걸 재조정합니다.

    • useState가 필요 없는 이유: "요청 → 응답 → setState → 리렌더"를 손으로 엮을 필요 없이, 서버가 변경 결과와 새 UI 설명을 한 번에 돌려주기 때문입니다. 상태의 소유자가 클라이언트에서 서버로 옮겨간 것
    • JS가 아직 로드되지 않았거나 비활성화돼 있어도 기본 HTML 폼 제출로 동작합니다 (점진적 향상)

  4. 함께 묻는 React 19 훅.

    • useActionState(action, initial) — 액션의 반환값을 상태로 받고 isPending 제공. 검증 에러 메시지 처리에 적합
    • useOptimistic — 서버 응답 전에 낙관적 UI를 먼저 보여주고, 응답이 오면 실제 상태로 수렴
    • useFormStatus — 폼 하위 컴포넌트에서 제출 상태를 읽어 버튼 비활성화

  5. 선택 기준. 콘텐츠 중심(상세 페이지, 목록, 검색 결과)·SEO·초기 로딩이 중요하면 Server Component. 애니메이션·드래그·window/localStorage 의존·고빈도 인터랙션은 클라이언트 컴포넌트. 경계를 트리 아래쪽에 두어 클라이언트 영역을 최소화하는 게 설계 요령입니다.

6. Virtual DOM · Diff · key에 index를 쓰면
7644859983968390777

질문 — Virtual DOM의 원리는? Diff는 실제로 어떻게 비교하나요? 리스트에 key를 왜 붙여야 하고, index를 key로 쓰면 왜 線上 버그가 나나요?

지원자 답변 — "JS 객체로 DOM을 흉내 내서 DOM 조작을 줄인다." → Diff 세부와 index key 문제에서 막힘.

정답

  1. Virtual DOM의 실제 가치는 "더 빠름"이 아니다. 손으로 최소 DOM 조작을 하는 것보다 빠를 수는 없습니다. 가치는 선언형 프로그래밍 모델입니다. "현재 상태에서 UI는 이렇게 생겨야 한다"만 쓰면, 어떤 DOM 조작으로 거기 도달할지는 React가 계산합니다. 부수적으로 변경을 모아 배치 적용하므로 불필요한 레이아웃/페인트가 줄어듭니다. 면접에서 "DOM 조작이 느려서 VDOM이 빠르다"로만 답하면 한 겹 더 파고듭니다.

  2. Diff(재조정)의 휴리스틱 3가지. 일반적인 트리 비교는 O(n³)이라 쓸 수 없어, React는 두 가지 가정으로 **O(n)**으로 낮춥니다.

    • 같은 레벨만 비교: 노드가 레벨을 넘어 이동하면 재사용하지 않고 폐기 후 재생성합니다. 그래서 조건부로 래퍼를 끼우면 하위 트리가 전부 언마운트됩니다
    • 타입이 다르면 폐기·재생성: <div> → <span>, ComponentA → ComponentB면 state까지 전부 버립니다
    • 타입이 같으면 속성만 갱신하고 자식으로 재귀

  3. key는 "리스트 항목의 신원"이다. key가 있으면 React는 위치가 아니라 신원으로 매칭해, 순서가 바뀐 항목은 이동으로 처리하고 state·DOM을 재사용합니다.

    • ⚠️ key가 없으면 React는 "O(n³)로 느려지는" 게 아니라 인덱스 기준으로 비교합니다. 성능이 폭락하는 게 아니라 동작이 틀려집니다. 이게 더 중요한 포인트입니다

  4. index를 key로 쓰면 생기는 실제 버그. 리스트 중간에 삽입/삭제/정렬이 일어나면 같은 index가 다른 데이터를 가리킵니다. React는 "같은 key니까 같은 항목"으로 보고 DOM과 state를 재사용합니다.

    • 입력 중이던 <input>의 값이 다른 행으로 옮겨 붙음
    • 체크박스 선택 상태가 엉뚱한 행에 남음
    • 애니메이션/트랜지션이 잘못된 요소에 적용됨
    • 자식 컴포넌트의 로컬 state가 섞임
    • 정상인 경우: 리스트가 정적이고 순서 변경·삽입·삭제가 전혀 없으며 항목에 state가 없을 때만 index가 안전합니다

  5. 올바른 key. 서버가 준 안정적 고유 ID(DB PK)를 씁니다. Math.random()이나 매 렌더마다 바뀌는 값은 매번 새 key = 매번 전체 재생성이라 최악입니다. 적절한 ID가 없으면 데이터 생성 시점에 한 번 ID를 부여해 두세요.

7. 박스 모델을 픽셀 단위까지 제어하기
7663062253184775921

질문 — 박스 모델에서 한 요소를 레이아웃 계산부터 픽셀 렌더링까지 정확히 제어하려면 어떤 속성들이 관여하고 우선순위는 어떻게 되나요?

지원자 답변 — content-box와 border-box의 차이만 말하고 막힘.

정답

  1. 기본 — 두 모드의 차이. content-box(기본값)에서 width는 콘텐츠 영역만 가리키고 padding·border는 바깥으로 더해집니다. border-box에서는 width가 border까지 포함합니다. 실무에서는 *, *::before, *::after { box-sizing: border-box }를 깔고 시작합니다. box-sizing은 상속되는 속성이 아니므로 전역 선택자로 지정하거나 box-sizing: inherit 패턴을 씁니다.

  2. 계산 규칙에서 자주 틀리는 것들.

    • padding/margin의 백분율은 가로·세로 모두 포함 블록의 너비 기준입니다. padding-top: 100%로 정사각형 비율을 만드는 기법이 여기서 나옵니다 (지금은 aspect-ratio를 쓰는 게 맞습니다)
    • 마진 상쇄(margin collapsing) 는 블록 레이아웃의 세로 마진에서만 발생합니다. 인접 형제 사이, 부모와 첫/마지막 자식 사이, 빈 블록의 자기 마진끼리. 차단하려면 BFC를 만들거나(display: flow-root, overflow: hidden, display: flex/grid) padding·border를 한 픽셀 끼웁니다. Flex/Grid 컨테이너 안에서는 마진 상쇄가 일어나지 않습니다
    • min-width/max-width가 width보다 우선합니다. 충돌 시 max-width → min-width 순으로 적용되므로 min-width가 최종 승자입니다

  3. 레이아웃 문맥에 따라 박스 모델이 다르게 동작한다.

    • display: inline은 width/height를 무시하고 세로 padding·margin이 줄 높이에 기여하지 않습니다. inline-block은 둘 다 적용되지만 공백 문자 때문에 간격이 생깁니다
    • Flex 아이템의 최종 크기는 flex-basis → flex-grow/flex-shrink → min-width/max-width 순으로 결정됩니다. 축소가 안 되는 고전적 원인은 min-width: auto(기본값)이며 min-width: 0으로 풉니다
    • position: absolute에서 width: 100%는 가장 가까운 position이 static이 아닌 조상의 패딩 박스 기준입니다. 자기 부모가 아닐 수 있다는 점이 함정
    • transform은 레이아웃 박스를 바꾸지 않습니다. 시각적으로만 이동/확대되므로 주변 요소는 원래 자리를 기준으로 배치됩니다. 반대로 getBoundingClientRect()는 변형된 결과를 돌려줍니다

  4. 공간을 차지하지 않는 것들. outline은 박스 크기에 포함되지 않아 레이아웃을 흔들지 않습니다(포커스 링에 적합). box-shadow도 공간을 차지하지 않습니다. 반면 border는 차지합니다. 포커스 표시에 border를 쓰면 1px씩 밀리는 이유입니다.

  5. 렌더링 성능으로 넘어가는 지점.

    • 레이아웃(리플로)을 유발하는 변경: width, height, margin, padding, top, left, font-size
    • 페인트만 유발: color, background-color, box-shadow, border-radius
    • 합성만 유발: transform, opacity, filter → 애니메이션은 이 둘만 쓰는 게 정석
    • contain: layout paint나 content-visibility: auto로 하위 트리의 레이아웃/페인트 범위를 격리해 긴 목록의 계산량을 줄입니다
    • will-change는 합성 레이어를 미리 만들지만 남발하면 레이어 폭증으로 GPU 메모리를 잡아먹어 오히려 느려집니다. 애니메이션 직전에 켜고 끝나면 제거하는 식으로만 씁니다
8. 좌측+상단 고정 반응형 관리자 레이아웃

질문 — 좌측 고정 내비게이션 + 상단 고정 헤더 + 가운데 콘텐츠 구조를 모바일부터 4K까지 대응하려면? float 때문에 부모 높이가 붕괴하는 문제는? 애니메이션 프레임을 어떻게 유지하나요?

지원자 답변 — "Flex 쓰고 안 되면 Grid, 그것도 안 되면 absolute. 애니메이션은 transition." → 되는 대로 시도하는 접근.

정답

  1. 레이아웃 모델 선택 기준 — "되는 걸 찾기"가 아니라 차원으로 고르기.
    • Grid = 2차원. 페이지 셸(사이드바 + 헤더 + 콘텐츠)은 Grid가 정답입니다. grid-template-areas로 이름을 붙이면 구조가 CSS에서 바로 읽힙니다
    • Flex = 1차원. 헤더 안의 로고/메뉴/프로필처럼 한 줄 배치에 씁니다
    • float는 레이아웃 도구가 아닙니다. 원래 용도(텍스트 둘러싸기) 외에는 쓰지 않습니다
.shell {
  display: grid;
  grid-template-areas: "aside header" "aside main";
  grid-template-columns: var(--aside-w, 240px) 1fr;
  grid-template-rows: 56px 1fr;
  height: 100dvh;                 /* 모바일 주소창 대응: vh 대신 dvh */
}
.shell > aside  { grid-area: aside;  overflow-y: auto; }
.shell > header { grid-area: header; position: sticky; top: 0; }
.shell > main   { grid-area: main;   overflow-y: auto; }

  1. 부모 높이 붕괴(height collapse) — 왜 생기고 어떻게 푸나. float된 자식은 일반 흐름에서 빠져 부모의 높이 계산에 기여하지 않습니다. 해법은 부모에 BFC(Block Formatting Context)를 만드는 것이고, 현대적인 방법은 display: flow-root 한 줄입니다. 레거시 clearfix(::after { content: ''; display: block; clear: both })나 overflow: hidden(의도치 않게 그림자/드롭다운을 자름)보다 깔끔합니다. 애초에 Flex/Grid를 쓰면 이 문제 자체가 발생하지 않습니다.

  2. 반응형 — 모바일 퍼스트 + 콘텐츠 기준 분기점.

    • 기본 스타일은 모바일로 쓰고 @media (min-width: ...)로 올려 갑니다
    • 분기점은 기기 모델이 아니라 콘텐츠가 깨지는 지점에서 잡습니다
    • 컴포넌트 단위 반응형은 컨테이너 쿼리(container-type: inline-size + @container)가 더 맞습니다. 같은 카드가 사이드바와 본문에서 다르게 보여야 할 때 미디어 쿼리로는 해결이 안 됩니다
    • 4K 대응은 "더 넓게 늘리기"가 아니라 max-width로 가독 폭을 제한하고 여백을 늘리는 쪽입니다
    • 단위: 폰트·간격은 rem, 유동 타이포는 clamp(1rem, 2vw, 1.5rem), 뷰포트 높이는 dvh/svh

  3. 레이아웃 흔들림(CLS) 막기. 이미지에 width/height 또는 aspect-ratio를 명시해 공간을 미리 확보합니다. 웹폰트는 font-display: swap과 size-adjust/폴백 메트릭 매칭으로 교체 시 밀림을 줄입니다. 반응형 이미지는 srcset/sizes.

  4. 애니메이션 프레임 유지. 애니메이션은 transform과 opacity만 건드립니다. 이 둘은 합성 단계에서 처리돼 레이아웃·페인트를 건너뜁니다. 사이드바 접기도 width 애니메이션 대신 transform: translateX()로 구현합니다. height: auto 전환이 필요하면 grid-template-rows: 0fr → 1fr이나 interpolate-size: allow-keywords를 씁니다. 그리고 prefers-reduced-motion을 존중합니다.

  5. 엔지니어링 — CSS도 아키텍처가 필요하다. 디자인 토큰을 CSS 커스텀 프로퍼티로 정의(색·간격·타이포·반경)해 테마 전환의 단일 소스로 삼고, 스코프 오염은 CSS Modules나 CSS-in-JS로 차단하고, stylelint로 규칙을 강제하고, 사용되지 않는 스타일은 빌드 단계에서 제거합니다. 선택자를 3단계 이상 중첩하지 않는 건 성능보다 유지보수 이유가 큽니다 (현대 브라우저의 선택자 매칭은 충분히 빠릅니다).

9. URL 입력부터 화면 표시까지
7654175198144978617

질문 — URL을 입력하고 엔터를 누른 뒤 화면이 보일 때까지 각 단계를 설명하고, 각 단계에 숨은 함정과 최적화 지점을 말하세요.

지원자 답변 — "DNS → TCP → HTTP 요청 → 렌더링" 암기한 순서는 유창. 각 단계의 세부와 최적화에서 막힘.

정답

  1. 입력 단계. 주소창 입력은 먼저 검색어인지 URL인지 판별하고, 스킴이 없으면 보정합니다. HSTS 목록에 있으면 HTTP 요청 없이 바로 HTTPS로 갑니다. 브라우저는 입력 중에 추측 도메인의 DNS를 미리 해석하기도 합니다(preresolve).

  2. 네트워크 단계.

    • DNS: 브라우저 캐시 → OS 캐시 → hosts → 로컬 DNS(ISP) → 루트/TLD/권한 네임서버. 최적화는 dns-prefetch, preconnect
    • 연결: TCP 3-way handshake + TLS handshake(TLS 1.3은 1-RTT, 세션 재개 시 0-RTT). HTTP/3는 QUIC(UDP) 위에서 돌아 연결 수립과 암호화 협상을 합쳐 RTT를 줄입니다
    • 프로토콜별 병렬성: HTTP/1.1은 도메인당 커넥션 6개 제한 → 도메인 샤딩이라는 우회책이 있었습니다. HTTP/2는 하나의 커넥션에서 멀티플렉싱하므로 샤딩이 오히려 해롭습니다
    • 캐시: Cache-Control: max-age/immutable로 강한 캐시(네트워크 요청 자체가 없음, DevTools에 200 from disk cache), 만료 후 ETag/If-None-Match 또는 Last-Modified/If-Modified-Since로 조건부 요청 → 변경 없으면 304(본문 없이 재검증). ETag가 Last-Modified보다 정확합니다(초 단위 해상도 문제가 없음). no-store(저장 금지)와 no-cache(저장하되 매번 재검증)를 혼동하지 마세요

  3. 파싱과 렌더링.

    • HTML을 위에서 아래로 파싱하며 DOM 구축. <script>(일반)는 파싱을 중단시키고 다운로드·실행까지 기다립니다. defer는 파싱을 막지 않고 DOM 완성 후 순서대로 실행, async는 파싱을 막지 않고 다운로드 완료 즉시 실행(순서 보장 없음), type="module"은 기본 defer
    • CSS는 DOM 구축은 막지 않지만 렌더 트리 구성과 렌더링을 막습니다(FOUC 방지). @import는 직렬 요청을 만들어 더 느립니다. 또한 CSSOM이 완성되기 전에는 스크립트도 실행되지 못합니다(스크립트가 스타일을 조회할 수 있으므로)
    • DOM + CSSOM → 렌더 트리 → 레이아웃 → 페인트 → 합성
    • 지표 매핑: TTFB(첫 바이트) → FCP(첫 콘텐츠 페인트) → LCP(최대 콘텐츠 페인트) → INP(상호작용 응답성). ⚠️ FID는 2024년 3월에 INP로 대체되었습니다. 영상들은 아직 FID를 언급하므로 면접에서는 INP로 답하세요

  4. 현대 브라우저의 추가 레이어.

    • preload(이 페이지에서 곧 필요 — 즉시 높은 우선순위), prefetch(다음 내비게이션에서 필요할 수도 — 유휴 시), preconnect(연결만 미리), dns-prefetch(DNS만). 구분해서 말하는 게 포인트
    • Service Worker가 요청을 가로채 오프라인 캐시·백그라운드 동기화를 수행
    • 리다이렉트(301/302)는 전체 네트워크 과정을 다시 타므로 체인이 길면 그대로 지연이 쌓입니다
    • content-visibility: auto로 화면 밖 영역의 렌더링을 건너뛰어 긴 페이지의 초기 렌더를 줄입니다

  5. 프로세스 모델 — "밑바닥"을 묻는 지점. 브라우저 프로세스(UI·네트워크 스택 조율), 렌더러 프로세스(사이트별 격리, Site Isolation), 네트워크 프로세스, GPU 프로세스로 나뉩니다. 렌더러의 메인 스레드가 JS 실행·스타일·레이아웃·페인트를 모두 담당하므로 긴 태스크 하나가 입력 응답을 막습니다. 그래서 작업을 쪼개거나(scheduler.yield(), requestIdleCallback) Web Worker로 옮깁니다. 합성은 별도 컴포지터 스레드에서 돌기 때문에 transform/opacity 애니메이션은 메인 스레드가 막혀도 부드럽게 돕니다.

10. POST 요청이 두 번 가는 이유
7699432397411122681

질문 — POST 요청이 왜 두 번 전송되나요? 크로스 오리진일 때 OPTIONS가 하나 더 가는 거 아닌가요? 그러면 GET은 왜 두 번 안 가죠? preflight는 정확히 무엇을 검사하나요?

지원자 답변 — 현상은 알지만 단순/비단순 요청 구분과 검사 내용을 설명하지 못함.

정답

  1. 현상. 크로스 오리진 POST가 비단순 요청(preflighted request) 조건에 걸리면, 브라우저가 실제 요청 전에 OPTIONS 메서드로 사전 전달(preflight) 요청을 보냅니다. 본문 없이 "이 오리진이 이 메서드와 이 헤더로 요청해도 되는지"만 묻습니다. 서버가 허용하면 실제 POST가 나갑니다. Network 패널에 2건이 보이는 이유입니다.

  2. 단순 요청(preflight 없음)의 조건 — 전부 만족해야 합니다.

    • 메서드가 GET, HEAD, POST 중 하나
    • 헤더가 CORS-safelisted만 사용 (Accept, Accept-Language, Content-Language, Content-Type, Range 일부 등)
    • Content-Type이 application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나
    • ReadableStream 본문이 아니고, XMLHttpRequest.upload에 이벤트 리스너가 없음

    그래서 GET이 두 번 안 가는 게 아닙니다. 커스텀 헤더(Authorization 등)를 붙인 GET도 preflight가 발생합니다. 반대로 Content-Type: text/plain인 POST는 preflight가 없습니다. 기준은 메서드가 아니라 조건 충족 여부입니다.

  3. preflight가 검사하는 것 / 응답 헤더.

    • 요청: Origin, Access-Control-Request-Method, Access-Control-Request-Headers
    • 응답: Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers, Access-Control-Allow-Credentials, Access-Control-Max-Age
    • 쿠키를 보내려면 credentials: 'include' + 서버의 Allow-Credentials: true, 그리고 Allow-Origin에 *를 쓸 수 없습니다(정확한 오리진을 echo해야 함)

  4. 최적화.

    • Access-Control-Max-Age로 preflight 결과를 캐시하는 게 가장 효과적입니다. 같은 오리진·메서드·헤더 조합이면 그 기간 동안 OPTIONS를 다시 보내지 않습니다. 단 Chromium은 상한이 7200초(2시간), Firefox는 86400초라 86400을 설정해도 Chrome에서는 2시간으로 깎입니다
    • 불필요한 커스텀 헤더를 줄여 단순 요청으로 만들기 (가능한 경우)
    • 가능하면 같은 오리진으로 프록시해 CORS 자체를 없애는 게 근본 해결입니다

  5. 백엔드 쪽 함정 — 성능이 아니라 정확성 문제. 서버가 OPTIONS를 구분하지 않고 비즈니스 로직까지 실행하면 중복 처리(중복 주문 생성 등) 가 발생할 수 있습니다. OPTIONS는 비즈니스 로직 전에 분기해 204 No Content로 바로 응답해야 합니다. 여기에 멱등성 설계를 더해 재시도에도 안전하게 만듭니다 (→ 12번 항목).

  6. 보안 레이어로 확장. Sec-Fetch-Site/Sec-Fetch-Mode/Sec-Fetch-Dest(Fetch Metadata)는 브라우저가 자동으로 붙이고 위조할 수 없어, 서버가 요청 출처 성격을 CORS 이전에 판단할 수 있습니다. 또한 공개 사이트가 사설망 주소로 요청할 때는 Private Network Access 관련 추가 검사가 적용되는 방향으로 표준이 진행 중입니다 — 다만 이 영역은 브라우저 버전마다 동작이 자주 바뀌므로, 면접에서는 "이런 방향의 제약이 추가되고 있다" 정도로 말하고 구체적 버전 숫자는 단정하지 않는 편이 안전합니다.

11. axios 요청 취소
7673086959510519483

질문 — axios로 요청을 취소할 수 있나요? 어떻게 구현하죠? CancelToken과 AbortController의 차이는? 실제 프로젝트에서 취소가 실패하거나 중복 요청이 나가는 이유와 해결은?

지원자 답변 — CancelToken은 언급. 두 방식의 차이, 에러 처리, 라우트 전환 시 일괄 취소에서 막힘.

정답

  1. 두 가지 방식.

    • CancelToken — axios 고유 API. 0.22.0부터 deprecated입니다. 레거시 코드 호환 목적으로만
    • AbortController — 브라우저 표준(fetch와 공유). axios 0.22+ 에서 signal 옵션으로 지원. 신규 코드는 이걸 씁니다. 표준이라 fetch·addEventListener·스트림과 같은 방식으로 다룰 수 있고, AbortSignal.timeout()이나 AbortSignal.any() 같은 조합이 가능합니다

  2. 중복 요청 취소 — pending 맵 패턴. 메서드 + URL + 직렬화한 파라미터로 키를 만들어 진행 중 요청을 Map에 보관하고, 같은 키가 또 들어오면 이전 것을 취소(또는 새 것을 버림)합니다. 인터셉터에 넣으면 호출부가 신경 쓸 필요가 없습니다.

const pending = new Map();
const keyOf = (c) => [c.method, c.url, JSON.stringify(c.params ?? {}), JSON.stringify(c.data ?? {})].join('|');

api.interceptors.request.use((config) => {
  const key = keyOf(config);
  pending.get(key)?.abort();                 // 이전 동일 요청 취소
  const controller = new AbortController();
  config.signal = controller.signal;
  pending.set(key, controller);
  return config;
});

api.interceptors.response.use(
  (res) => { pending.delete(keyOf(res.config)); return res; },
  (err) => { if (err.config) pending.delete(keyOf(err.config)); return Promise.reject(err); }
);

"취소가 실패한다"는 호소의 대부분은 응답/에러 시 맵에서 지우지 않아 키가 남거나, 두 방식을 섞어 써서 signal이 덮어써진 경우입니다.

  1. 라우트 전환 시 일괄 취소. 전역 컨트롤러 집합을 두고 라우터 가드(또는 React의 useEffect cleanup)에서 전부 abort()합니다. 떠난 화면의 응답이 늦게 도착해 사라진 컴포넌트에 setState하거나 전역 로딩을 꺼 버리는 사고를 막습니다.

  2. 에러 처리 — 취소는 실패가 아니다. 취소된 요청도 reject로 떨어집니다. 이걸 일반 에러로 처리하면 사용자에게 "요청 실패" 토스트가 뜹니다. 반드시 분기해서 조용히 무시해야 합니다.

    • axios: axios.isCancel(err) 또는 err.code === 'ERR_CANCELED'
    • fetch: err.name === 'AbortError'

  3. 마무리. 취소는 "요청을 되돌리는" 게 아닙니다. 서버에는 이미 도착해 처리될 수 있습니다. 브라우저가 응답을 버리는 것일 뿐이므로, 중복 생성을 막아야 하는 쓰기 작업은 취소에 의존하지 말고 서버 멱등성으로 보장해야 합니다 (→ 12번).

12. 프론트엔드 요청 멱등성 설계
7674949459806232250

질문 — 극단적인 네트워크 환경에서 사용자가 제출 버튼을 빠르게 두 번 눌렀을 때, 주문이 하나만 생기도록 보장하는 방안을 설계하세요. 디바운스/스로틀로 대충 막는 건 안 됩니다.

지원자 답변 — "인터셉터에서 매 요청마다 고유 RequestID를 만들어 헤더로 넘기고 서버가 멱등 처리" → ID 생성 방식, 탭 간 고유성, 토큰 만료, 서버 저장소 장애에서 전부 막힘.

정답

  1. 먼저 분명히 할 것 — 멱등성은 서버가 보장한다. 프론트엔드는 같은 논리적 작업에 같은 키를 붙여 재시도해 주는 역할이고, 중복 차단의 최종 책임은 서버에 있습니다. "프론트엔드 멱등성 방안"이라는 질문에 프론트엔드만으로 보장하겠다고 답하면 틀립니다. 디바운스/스로틀은 UX 개선이지 보장이 아닙니다(네트워크 재시도, 탭 복제, 뒤로가기 재제출을 막지 못함).

  2. 멱등성 키 설계.

    • 작업 단위로 한 번 생성해 재시도 전체에서 재사용합니다. 요청마다 새로 만들면 멱등성이 없어집니다. "장바구니 체크아웃 화면에 진입할 때 키 1개 발급"이 맞는 단위입니다
    • 생성은 crypto.randomUUID() 로 충분합니다. 충돌 확률이 무시할 수준이고 표준 API입니다
    • ⚠️ 영상 정정 1 — UUID 36바이트를 아끼려고 커스텀 포맷(타임스탬프+클라이언트 지문+시퀀스)을 설계하자는 제안은 과도합니다. 요청당 36바이트는 TLS 레코드 하나보다 작습니다. 복잡한 자체 ID 체계는 충돌·시계 역행·디버깅 난이도라는 실제 비용을 만듭니다
    • ⚠️ 영상 정정 2 — Canvas 핑거프린팅으로 클라이언트 지문을 만들자는 제안은 쓰지 마세요. 사용자 추적 기술이라 개인정보 규제(GDPR 등) 대상이고, 브라우저들이 적극적으로 차단·노이즈를 넣고 있어 안정적이지도 않습니다. 멱등성에는 지문이 필요 없습니다 — 랜덤 UUID가 더 안전하고 확실합니다

  3. 재시도·복구를 견디게 만들기.

    • 발급한 키를 sessionStorage에 저장해 새로고침·탭 복구 후에도 같은 키로 이어 갑니다. 작업 완료 시 삭제
    • 네트워크 타임아웃 후 재시도는 반드시 같은 키로 보냅니다. 서버는 이미 처리했다면 저장된 결과를 그대로 돌려줍니다 (새 리소스를 만들지 않음)
    • 탭 간 조율이 필요하면 BroadcastChannel로 "이 작업 진행 중" 신호를 공유합니다. 단 이건 UX 개선이고 보장이 아닙니다 — 서버가 같은 키를 보고 걸러야 합니다
    • 버튼은 요청 진행 중 비활성화 + 낙관적 UI로 이중 제출 자체를 줄입니다 (1차 방어선)

  4. 서버 측 — 실제 보장 계층. 프론트엔드 설계를 설명할 때 이 부분을 같이 말해야 "전체를 안다"는 평가를 받습니다.

    • 멱등성 키를 저장소(Redis 등)에 기록하고, 같은 키의 재요청은 저장된 응답을 재생
    • 캐시 계층의 신뢰성에 의존하지 않도록 DB 유니크 제약을 최종 방어선으로 둡니다. 이게 Redis 장애·스플릿 브레인·노드 전환 같은 모든 상황에서 중복을 막는 유일한 확실한 수단입니다
    • 키의 TTL은 작업 특성에 맞게 (주문이면 수십 분~수 시간)
    • 업계 관례: Idempotency-Key 헤더 (Stripe 등 결제 API의 사실상 표준)

  5. 모니터링. 멱등 충돌(중복 차단) 비율, 재시도 비율, 키 발급 대비 완료율을 지표로 남깁니다. 충돌률이 갑자기 오르면 네트워크 품질 저하나 클라이언트 버그의 신호입니다.

  • Tree shaking이 실패하는 조건을 알아야 합니다: ES Module(import/export)만 정적 분석이 가능합니다. CommonJS(require)는 안 됩니다. 또 package.json의 sideEffects: false 선언이 없으면 번들러가 제거를 포기합니다. 라이브러리가 CJS만 제공하거나 사이드 이펙트를 선언하지 않으면 "tree shaking 했는데 안 줄어드는" 상황이 생깁니다
  • 공통 청크 분리: 자주 바뀌지 않는 벤더 코드를 별도 청크로 빼서 브라우저 캐시를 재사용. 단 과도하게 쪼개면 요청 수가 늘고 캐시 무효화 범위만 복잡해집니다
  • 서드파티 10개 처리: 번들 분석기로 실제 기여도를 보고 ① 필요 없으면 제거 ② 일부만 쓰면 하위 경로 import 또는 경량 대체 ③ 첫 화면에 불필요하면 동적 import로 지연 ④ 분석/광고 스크립트는 async + 사용자 상호작용 이후 로드
  • 바이트 압축: gzip보다 Brotli가 텍스트 자원에서 15~20% 더 작습니다

2단계: 네트워크 — 더 빨리, 더 적게 가져온다

  • CDN: 지리적 지연 감소 + 원본 대역폭 절감
  • HTTP/2·HTTP/3: 하나의 커넥션에서 멀티플렉싱하므로 HTTP/1.1 시절의 도메인 샤딩은 쓰면 안 됩니다(커넥션이 쪼개져 오히려 손해). 영상의 "도메인을 나눠 6개 제한을 돌파" 조언은 HTTP/1.1 전제의 낡은 처방입니다
  • 리소스 힌트 — 구분이 질문의 핵심입니다
    힌트 의미 쓰는 곳
    preload 이 페이지에서 곧 필요 → 즉시 높은 우선순위로 받기 첫 화면 폰트, 크리티컬 CSS, LCP 이미지
    prefetch 다음 내비게이션에서 필요할 수도 → 유휴 시 낮은 우선순위 다음 페이지 청크
    preconnect 연결만 미리 (DNS+TCP+TLS) CDN, 서드파티 API 도메인
    dns-prefetch DNS만 미리 preconnect 미지원 폴백
    • preload는 남발하면 진짜 중요한 자원의 우선순위를 깎아먹습니다. as 속성을 반드시 지정하고, 폰트는 crossorigin도 필요합니다
  • 캐시 계층: 해시 파일명 + Cache-Control: max-age=31536000, immutable(정적 자원), no-cache(HTML 엔트리). 이 조합이 뒤바뀌면 배포해도 사용자가 구버전에 머뭅니다 (→ 26번)

3단계: 렌더링 — 더 빨리 보이게 한다

  • 크리티컬 CSS 인라인 + 나머지는 비동기 로드. CSS는 렌더를 막기 때문에 효과가 큽니다
  • JS는 defer/async 로 파싱 차단 제거
  • 이미지: AVIF/WebP, srcset/sizes로 해상도별 제공, 첫 화면 밖은 loading="lazy", 첫 화면 LCP 이미지는 절대 lazy로 만들지 말고 fetchpriority="high"를 줍니다. 크기 명시로 CLS 방지
  • 스켈레톤/LQIP: 체감 속도를 올립니다. 단 실제 LCP 수치는 개선되지 않으므로 지표와 체감을 구분해서 말하세요
  • content-visibility: auto 로 화면 밖 섹션의 렌더 비용 제거

4단계: 런타임 — 보인 뒤에도 매끄럽게

  • 긴 목록은 가상 스크롤, 입력은 디바운스·스크롤은 스로틀, 무거운 계산은 Web Worker
  • 긴 태스크는 scheduler.yield()/postTask로 쪼개 입력 응답성(INP) 확보

5단계: 측정과 고착 방지 — 이 단계가 "체계적"의 핵심

  • 코어 웹 바이탈: LCP(≤2.5s), INP(≤200ms), CLS(≤0.1). ⚠️ 영상은 FID를 말하지만 2024년 3월 INP로 공식 대체되었습니다
  • 실사용자 모니터링(RUM)으로 네트워크·기기·지역별로 분해해서 봅니다. 평균이 아니라 p75를 봅니다
  • CI에 번들 크기 예산을 걸어 임계값 초과 시 빌드를 실패시킵니다. 안 그러면 몇 달 뒤 원점으로 돌아갑니다
  • 약한 네트워크·저사양 기기용 폴백: 비핵심 애니메이션 off, 비필수 모듈 지연, 타임아웃 시 스켈레톤 유지

면접관이 실제로 보는 건 "기법 나열"이 아니라 ① 측정으로 병목을 찾았는지 ② 각 조치의 예상 수익을 수치로 말하는지 ③ 우선순위를 매겼는지입니다. "이미지 압축으로 0.3초, 라우트 분할로 1.2초, 크리티컬 CSS로 0.6초" 식으로 말하는 게 정답에 가깝습니다.

14. 스크롤이 슬라이드쇼처럼 끊김
7651945694047474917

질문 — 사용자가 스크롤할 때 화면이 슬라이드쇼처럼 끊깁니다. 어떻게 원인을 찾고 최적화하나요?

지원자 답변 — "DOM 줄이고 디바운스 걸겠습니다." → 진단 절차 없이 처방부터.

정답

  1. 먼저 증상을 구분한다. 네 가지는 원인이 전혀 다릅니다.

    • 버벅임(jank): 프레임 드롭 — 메인 스레드가 16.7ms를 넘김
    • 입력 지연: 스크롤 시작이 늦게 반응 — 긴 태스크나 non-passive 리스너
    • 깜빡임(flicker): 페인트 순서·레이어 문제
    • 빈 화면(blank): 가상 리스트의 렌더가 스크롤 속도를 못 따라감 그리고 전역 스크롤인지 특정 컨테이너 스크롤인지 범위를 좁힙니다.

  2. 진단 — 추측 말고 측정. DevTools Performance로 스크롤을 녹화하고 순서대로 봅니다.

    • 프레임 차트에서 길어진 프레임을 찾습니다
    • 그 프레임에서 시간을 먹는 게 Scripting / Rendering(Style+Layout) / Painting 중 무엇인지 봅니다. 이 분류만으로 처방이 갈립니다
    • "Forced reflow" 경고가 가장 흔한 범인입니다
    • Layers 패널로 합성 레이어 수와 메모리를 확인합니다
    • Performance.measureUserAgentSpecificMemory()나 Memory 패널로 누수 여부 확인

  3. 레이아웃 스래싱 — 가장 흔한 원인. 쓰기 직후 읽기를 반복하면 브라우저가 매번 강제로 레이아웃을 동기 계산합니다.

// 나쁨: 읽기-쓰기 교차 → 매 반복마다 강제 레이아웃
items.forEach(el => { el.style.height = el.offsetHeight + 10 + 'px'; });

// 좋음: 읽기 전부 → 쓰기 전부
const hs = items.map(el => el.offsetHeight);
items.forEach((el, i) => { el.style.height = hs[i] + 10 + 'px'; });

offsetTop, offsetHeight, scrollTop, getBoundingClientRect(), getComputedStyle()이 강제 레이아웃을 유발하는 읽기입니다.

  1. 스크롤 리스너. addEventListener('scroll', fn, { passive: true }) — passive가 없으면 브라우저는 preventDefault() 가능성 때문에 스크롤을 리스너 실행까지 기다립니다. touchstart/touchmove도 동일. 스크롤 핸들러 안에서는 레이아웃 읽기나 DOM 쓰기를 하지 말고, 필요하면 requestAnimationFrame으로 프레임당 1회로 모읍니다. 요소 가시성 판단은 스크롤 핸들러 대신 IntersectionObserver 를 씁니다(메인 스레드 밖에서 동작).

  2. 디바운스 vs 스로틀 — 잘못 쓰면 더 나빠집니다.

    • 디바운스: "멈추면 한 번" — 검색 입력, 창 리사이즈 완료
    • 스로틀: "주기적으로" — 스크롤 위치 추적, 무한 스크롤 트리거
    • 스크롤 위치에 디바운스를 걸면 스크롤 중에는 아무 반응이 없습니다. 반대로 검색에 스로틀을 걸면 불필요한 요청이 계속 나갑니다
    • 시각적 갱신은 둘 다 아니라 rAF 스로틀이 맞습니다

  3. 렌더링 계층 최적화.

    • 애니메이션은 transform/opacity만. will-change는 애니메이션 직전에만 (남발 시 레이어 폭증 → GPU 메모리 → 더 느려짐)
    • 스크롤 영역 안에서 box-shadow, filter, backdrop-filter, 큰 border-radius, 그라디언트는 페인트 비용이 큽니다. 특히 backdrop-filter는 모바일에서 치명적입니다
    • position: fixed 요소가 스크롤 영역과 겹치면 매 프레임 재합성됩니다
    • content-visibility: auto + contain-intrinsic-size로 화면 밖 렌더 건너뛰기
    • CSS overscroll-behavior: contain으로 스크롤 체이닝 차단
    • 가능하면 JS 스크롤 하이재킹(커스텀 스무스 스크롤)을 쓰지 않습니다. 네이티브 스크롤은 컴포지터 스레드에서 돌지만 JS 구현은 메인 스레드로 끌어내립니다

  4. 극단 케이스. 1만 행 이상은 가상 스크롤(→ 15번). 메모리 누수로 시간이 지나며 점점 느려지는 패턴은 타이머·리스너·클로저 잔존을 의심합니다. 저사양 기기에서는 애니메이션 off·동시 요청 제한 같은 점진적 성능 저하(graceful degradation) 를 적용합니다.

15. 가상 리스트를 썼는데도 5000행 테이블이 끊김
7659725731376053873

질문 — 5000행 편집 가능 테이블에 가상 리스트를 이미 넣었는데도 스크롤이 끊기고 입력이 늦습니다. 화면에 20개만 그리는데 왜 끊기나요?

지원자 답변 — "데이터가 많아서, 행 높이 캐시를 안 켜서" → 편집 가능 셀, 셀 병합, 실시간 검증, 고정 열 같은 테이블 고유 요인을 고려하지 못함.

정답 — "가상 리스트를 썼는데도 끊긴다"는 건 DOM 개수가 아닌 다른 병목이 있다는 뜻입니다. 네 방향으로 나눠 봅니다.

  1. 가상화 자체의 설정 문제

    • 동적 행 높이: 고정 높이를 가정했는데 셀 텍스트가 줄바꿈되면 오프셋이 어긋나 스크롤 중 지속적인 재측정·재배치가 발생합니다. 측정 캐시(ResizeObserver로 실측 후 캐시) 또는 추정 높이 + 점진 보정 전략이 필요합니다
    • 오버스캔(버퍼) 크기: 너무 작으면 빠른 스크롤에서 빈 화면, 너무 크면 렌더량이 늘어 끊김. 보통 화면 행 수의 30~50%
    • 스크롤 컨테이너의 overflow/position 설정이 뷰포트 계산을 틀어지게 하는 경우

  2. 데이터 계층 — 5000행을 "메모리에 들고 있는 것" 자체의 비용

    • 편집 가능 테이블에서 5000행을 양방향 바인딩하면 입력 1회가 전체 데이터 변경 감지를 유발할 수 있습니다. Vue 2의 깊은 반응성, React의 "전체 배열 교체 → 모든 행 props 변경"이 여기 해당
    • 해법: 행 단위 불변 갱신(변경된 행만 새 객체), 셀 단위 로컬 state로 입력 중에는 상위를 건드리지 않고 blur/디바운스 시점에만 커밋
    • 서버 페이지네이션이 가능하면 그게 가장 확실합니다. "프론트에서만 슬라이스"는 여전히 전체를 파싱·보관합니다

  3. 테이블 고유 요인 — 단순 리스트와 결정적으로 다른 부분

    • 편집 가능 셀: 스크롤 중 <input>이 생성·파괴되면 포커스/IME 상태와 함께 비용이 큽니다. 입력 컴포넌트는 셀 클릭 시에만 마운트하고 평소에는 텍스트로 렌더합니다
    • 고정 헤더/고정 열: 구현이 좌·우 두 개의 테이블을 겹치는 방식이면 렌더량이 2배가 됩니다. CSS position: sticky로 단일 테이블 안에서 처리하는 편이 훨씬 가볍습니다
    • 셀 병합(rowspan/colspan): 행 높이 계산 전제를 깨뜨려 가상화와 충돌합니다. 병합이 필요하면 가상화 단위를 "행"이 아니라 "병합 그룹"으로 잡아야 합니다
    • 실시간 검증·행 하이라이트·드래그 정렬: 스크롤 중에도 콜백이 계속 돌아 메인 스레드를 점유합니다. 스크롤 중에는 중단하고 정지 후 재개하는 전략

  4. 브라우저 밑바닥 — 근본 처방

    • 강제 동기 레이아웃: 행 높이를 위해 스크롤 중 offsetHeight를 읽으면 매 프레임 레이아웃이 동기 실행됩니다. 이게 "가상 리스트인데 끊기는" 가장 흔한 범인입니다. 측정은 스크롤 전/후에, 결과는 캐시
    • 레이어 관리: 고정 헤더만 별도 레이어로 승격하고, 모든 행에 will-change를 뿌리지 않습니다
    • 메모리 누수: 행 언마운트 시 입력 이벤트·타이머·옵저버를 해제하지 않으면 스크롤할수록 느려집니다("점점 느려짐" 패턴의 지표)
    • Web Worker: 5000행의 정렬·필터·오프셋 누적 계산을 워커로 옮겨 메인 스레드를 비웁니다
    • contain: strict/content-visibility로 행 단위 렌더 격리

한 줄 요약: 이 질문이 가리는 건 "가상 리스트 라이브러리를 쓸 수 있는지"가 아니라 DOM 개수 외의 병목을 측정으로 분리할 수 있는지입니다.

16. 실시간 대시보드 리렌더 폭주, 30fps
7659354661753767141

질문 — 대시보드에 꺾은선 20여 개와 숫자 카드가 있고 1초마다 폴링합니다. 지표 2개만 바뀌는데도 전체 컴포넌트가 리렌더되고 React.memo가 전혀 안 먹습니다. 프레임이 30 이하로 떨어졌습니다. 원인과 해결은?

지원자 답변 — "memo로 감싸고 useMemo로 데이터 캐시." → 왜 memo가 무력화되는지 설명 못함.

정답

  1. memo가 안 먹는 이유 — 참조 동일성. React.memo는 props를 얕게 비교합니다. 폴링 응답은 매번 새 배열·새 객체이므로 내용이 같아도 참조가 달라 비교를 통과합니다. useMemo로 감싸도 의존성 배열에 그 새 객체가 들어 있으면 매번 재계산됩니다. 여기에 단일 전역 스토어에 모든 지표를 넣어 두면, 지표 하나가 바뀌어도 스토어 객체가 교체되어 구독한 모든 컴포넌트가 깨어납니다. 세 요인이 겹친 결과입니다.

  2. 진단 순서.

    • React DevTools Profiler: "Why did this render?"로 어떤 prop이 바뀌었는지 확인. Highlight updates로 불필요한 리렌더를 눈으로 봅니다
    • DevTools Performance: 메인 스레드에서 JS(React 렌더)와 Canvas 그리기(차트) 중 어느 쪽이 시간을 먹는지 분리
    • 중요한 구분: React 리렌더와 차트 라이브러리의 캔버스 재그리기는 서로 다른 두 개의 성능 문제입니다. React 리렌더를 0으로 만들어도 차트가 매초 전체 재그리기를 하면 여전히 30fps입니다

  3. 데이터 흐름 교정 — 핵심 처방.

    • 스토어 분할 + 선택적 구독: 각 차트가 자기 지표만 구독합니다. Zustand의 선택자, Redux의 메모이즈된 셀렉터, Jotai의 원자 단위 등. "지표 하나 변경 → 해당 컴포넌트 하나만 리렌더"가 목표
    • 참조 안정화: 서버 응답을 받자마자 변경된 필드만 교체하는 불변 갱신을 수행해, 바뀌지 않은 지표의 참조를 유지합니다. 이것만으로 memo가 되살아납니다
    • 응답 동일성 검사: 직전 응답과 값이 같으면 스토어를 아예 갱신하지 않습니다 (폴링에서 가장 효과적인 한 줄)
    • 타임스탬프나 요청 ID 같은 매번 바뀌는 메타 필드를 지표 객체에 섞지 않습니다 — 이것 하나로 모든 memo가 무력화됩니다
    • 콜백은 useCallback, 포맷팅 함수는 컴포넌트 밖 모듈 스코프로

  4. 타이머 생명주기. setInterval을 컴포넌트 안에서 걸고 cleanup하지 않으면 라우트를 옮겨도 폴링이 계속되고, 재진입 시 중첩됩니다. useEffect의 cleanup에서 반드시 해제하고, ref에 ID를 보관합니다. 추가로 document.visibilitychange로 탭이 숨겨지면 폴링을 멈추거나 간격을 늘립니다 — 체감 비용 대비 효과가 가장 큰 조치입니다.

  5. 차트(캔버스) 쪽 최적화.

    • 데이터 포인트 다운샘플링: 1000포인트를 1px 폭에 그릴 이유가 없습니다. 화면 폭 기준으로 샘플링(LTTB 등)
    • 전체 재그리기 대신 증분 갱신 지원 여부 확인 (ECharts의 setOption(opt, { notMerge: false }), 스트리밍 모드 등)
    • 애니메이션·그라디언트·그림자 off (대시보드에서는 비용만 큽니다)
    • ResizeObserver 폭주: 리사이즈마다 차트 resize()를 호출하면 레이아웃-재그리기 루프가 생깁니다. rAF로 합치고 디바운스
    • 차트 인스턴스는 useRef에 보관해 리렌더마다 재생성되지 않게 합니다 (재생성이 느려지는 가장 큰 단일 원인)
    • 무거운 집계는 Web Worker로

  6. 점진적 성능 저하. FPS를 실측해 임계값 아래로 떨어지면 애니메이션 off → 폴링 간격 증가 → 표시 지표 수 축소 순으로 자동 강등합니다. 개발 환경에서는 전체 렌더, 운영에서는 강등 정책을 켜 두는 구성도 흔합니다.

17. 백화면율 정의와 線上 원인 추적
7661959349305075643

질문 — 서비스의 백화면율(白屏率)이 얼마이고 기준을 어떻게 정의했나요? 사용자가 첫 화면이 느리다고 항의할 때 원인 추적 과정을 설명하세요.

지원자 답변 — "대략 몇 천분의 몇, 화면이 비어 있으면 백화면." → 짧은 공백과 실제 장애를 구분하지 못하고 측정 체계가 없음.

정답

  1. 정의부터 합의해야 합니다 — 기준 없는 수치는 의미가 없습니다.

    • 분모를 PV로 할지 UV로 할지 먼저 정합니다 (보통 PV)
    • 판정 규칙 예시: "페이지 진입 후 N초 내에 뷰포트 안에 유효한 콘텐츠 노드(텍스트·이미지)가 렌더되지 않음". N은 서비스 특성에 맞게 정하고 문서화합니다
    • 짧은 로딩 공백은 백화면이 아닙니다. 스켈레톤이 떠 있는 상태도 백화면이 아닙니다 (사용자는 "진행 중"으로 인지)
    • 원인별로 분리 집계: ① 리소스 로드 실패(JS/CSS 404·5xx) ② JS 런타임 에러로 렌더 중단 ③ API 지연·실패 ④ 렌더는 됐지만 콘텐츠가 비어 있음(데이터 공백). 이걸 하나로 뭉치면 개선 방향이 안 나옵니다

  2. 지표 연동. 백화면은 독립 지표가 아니라 FCP/LCP의 극단 꼬리입니다. LCP p99가 나쁘면 백화면율도 올라갑니다. FCP(첫 픽셀), LCP(주요 콘텐츠), TTI/INP(조작 가능)와 함께 봐야 원인이 어디쯤인지 좁혀집니다.

  3. 탐지 구현.

    • DOM 샘플링: 특정 시점에 루트 컨테이너의 유효 자식 노드 수·텍스트 길이를 검사. 가장 단순하지만 오탐이 있습니다
    • PerformanceObserver로 paint/largest-contentful-paint 수집: 일정 시간 내 FCP 이벤트가 없으면 백화면 후보로 표시. 표준 API라 신뢰도가 높습니다
    • 에러 채널: window.onerror, unhandledrejection, 그리고 리소스 로드 실패를 잡는 캡처 단계 error 리스너(window.addEventListener('error', fn, true))
    • 경계 처리: SPA 라우트 전환 백화면, 마이크로 프론트엔드 하위 앱 백화면, 모바일 WebView 호환성 문제는 각각 별도로 식별해야 합니다
    • 차원 태깅: 기기·OS·브라우저 버전·네트워크 유형·앱 버전·지역·CDN 노드. 이게 없으면 "전체 0.3%" 같은 숫자만 남고 원인에 못 닿습니다

  4. "첫 화면이 느리다" 신고 처리 — 표준 절차. 바로 최적화에 들어가지 않고 계층별로 좁힙니다.

    • 네트워크층: 리소스 크기, 직렬 요청 체인, CDN 노드 응답, DNS 시간, TTFB
    • JS 실행층: 긴 태스크, 불필요한 서드파티 SDK, 파싱·컴파일 시간
    • 렌더층: 크리티컬 CSS 누락, 폰트 차단, 대량 리플로, 이미지 미최적화
    • API층: 첫 화면 요청의 직렬화, 페이지네이션 부재, 타임아웃 시 폴백 없음 각 층에서 실측치를 뽑아 가장 큰 기여 구간부터 처리합니다.

  5. 폴백 설계 — 모니터링과 함께 가야 하는 쌍.

    • 크리티컬 CSS 인라인으로 "CSS 로드 실패 = 완전 백지"를 방지
    • 동적 import 실패를 잡아 캐시 정리 후 재로드 (→ 26번)
    • 백업 CDN·재시도
    • JS 전면 실패 시에도 HTML에 최소 안내 문구가 남게 (<noscript> + 서버 렌더 셸)
    • 사용자 세그먼트별 차별화: 저사양·약한 네트워크에는 경량 번들

  6. 장기 운영. 채널·버전·기기별 백화면율 대시보드와 알림 임계값, 그리고 CI 게이트(번들 크기·긴 태스크 증가 시 차단)로 회귀를 막습니다. 개선 효과는 "백화면율 x% → y%, LCP p75 a초 → b초, 전환율 변화"처럼 비즈니스 지표와 묶어 보고합니다.

18. 번들 크기 — 같은 라이브러리가 두 번 들어감
7678643363441219259

질문 — 번들이 너무 큽니다. 프로젝트가 lodash를 쓰고, 어떤 서드파티 차트 라이브러리도 lodash에 의존합니다. 결과적으로 lodash가 두 번 들어갔습니다. splitChunks의 cacheGroups로 뽑아내려 했는데도 여전히 두 벌입니다. 왜죠? 버전이 4.17과 4.20으로 다르면 어떻게 합쳐야 하나요? 호환되지 않는데 강제로 합치면 버그가 나지 않나요?

지원자 답변 — "splitChunks, 압축, tree shaking, CDN" 나열. 버전 불일치가 원인임은 짐작했지만 해결 방법을 말하지 못함.

정답

  1. 왜 안 합쳐지는가 — 의존성 트리의 중첩 설치. 패키지 매니저는 서로 다른 버전을 요구하면 node_modules/lodash(4.17)와 node_modules/some-chart/node_modules/lodash(4.20)로 각각 설치합니다. 번들러에게 이 둘은 완전히 다른 모듈입니다. 경로가 다르므로 splitChunks가 같은 그룹으로 모아도 두 벌이 그대로 남습니다. splitChunks는 중복을 제거하는 도구가 아니라 청크를 나누는 도구라는 점이 질문의 핵심입니다.

  2. 1단계: 진단 — 몇 벌이, 어디서 왔는지 확정

    • webpack-bundle-analyzer(또는 rollup-plugin-visualizer, vite-bundle-visualizer)로 중복 모듈을 시각적으로 확인
    • npm ls lodash / pnpm why lodash / yarn why lodash 로 누가 어떤 버전을 끌어오는지 정확히 특정
    • 추측하지 말고 이 두 명령 결과를 근거로 말하는 게 정답의 전제입니다

  3. 2단계: 버전 통일 — 근본 해결

    • overrides(npm 8.3+) / resolutions(Yarn) / pnpm.overrides 로 모든 하위 의존성이 한 버전을 쓰도록 강제합니다
    { "overrides": { "lodash": "4.17.21" } }
    • 여기서 중요한 단서: overrides는 semver 호환 범위 내에서만 안전합니다. 4.17 ↔ 4.20은 같은 메이저라 보통 안전합니다. 하지만 메이저가 다르면(예: 3.x ↔ 4.x) 강제 통합은 런타임 에러를 만듭니다. 영상이 "호환 안 되면 버그 나지 않나?"라는 추궁에 답을 못 한 지점이 바로 여기이고, 정답은 "semver 호환이면 통일, 비호환이면 통일하지 않고 분리 유지" 입니다
    • 가능하면 해당 서드파티를 최신으로 올려 요구 버전을 맞추는 게 가장 깔끔합니다
    • pnpm은 기본적으로 엄격한 구조라 유령 의존성을 막아 이런 문제의 발생 자체를 줄입니다

  4. 3단계: 통일이 불가능할 때

    • 두 메이저 버전을 각각 별도 벤더 청크로 분리합니다. 중복은 남지만 비즈니스 코드에 섞여 들어가지 않아 캐시 효율은 지킬 수 있습니다
    • resolve.alias로 특정 라이브러리의 하위 의존을 다른 경량 구현으로 교체 (예: moment → dayjs)
    • 해당 서드파티를 제거하거나, 필요한 함수만 직접 구현해 의존을 끊습니다

  5. 동시에 할 수 있는 번들 축소 조치

    • 하위 경로 import: import debounce from 'lodash/debounce' 또는 lodash-es + tree shaking. import { debounce } from 'lodash'(CJS)는 전체를 끌어옵니다
    • 무거운 라이브러리 교체: moment→dayjs/date-fns, 전체 아이콘 팩→필요한 것만
    • 비핵심 모듈은 동적 import()
    • sideEffects: false 선언 확인 (없으면 tree shaking이 포기합니다)
    • 폴리필 과다 확인: browserslist를 실제 지원 대상으로 좁히면 크게 줄어듭니다
    • CI에 번들 크기 예산을 걸어 재발 방지

이 질문이 선별하는 능력: splitChunks 설정 암기가 아니라 의존성 트리를 읽고 semver 호환성을 판단하는 엔지니어링 감각입니다.

19. 마이크로 프론트엔드로 쪼갰는데 더 느려짐
7654881147059477157

질문 — 모놀리식 앱을 마이크로 프론트엔드로 분할했는데 반년 뒤 화면 전환 시 백화면, 라우팅 지연, 메모리 지속 증가로 분할 전보다 느려졌습니다. 어떤 기준으로 쪼갰고, 분할 입도는 어떻게 정했나요?

지원자 답변 — "업무 모듈별로 쪼개고 라우트로 나눴습니다." → 공통 의존성, 전역 스토어, 스타일 격리, 샌드박스 설정, 리소스 중복 로드를 고려하지 않음.

정답

  1. 마이크로 프론트엔드의 목적을 먼저 확인합니다. 얻는 것은 조직적 독립성(팀별 독립 배포·기술 스택 선택·릴리스 주기)이고, 치르는 비용은 런타임 오버헤드와 운영 복잡도입니다. 성능 개선이 목적이라면 애초에 잘못된 선택입니다 — 코드 분할과 라우트 레벨 lazy loading으로 충분합니다. 이 트레이드오프를 말하는 것이 질문의 첫 관문입니다.

  2. 느려진 원인 1: 공통 의존성 중복 로드 — 가장 큰 범인. 각 하위 앱이 React/Vue·UI 컴포넌트 라이브러리·axios·날짜 라이브러리를 자기 번들에 포함해 독립 빌드하면, 화면을 옮길 때마다 같은 코드를 다시 다운로드·파싱·실행합니다. 해법:

    • Module Federation의 shared 로 단일 인스턴스 공유 (singleton: true, requiredVersion로 호환 범위 지정)
    • 또는 import maps + externals: 공통 라이브러리를 셸이 한 번 로드하고 하위 앱은 전역에서 참조
    • 공유 대상은 "크고, 자주 안 바뀌고, 인스턴스가 하나여야 하는 것"(프레임워크 런타임, 라우터, UI 라이브러리). 작은 유틸은 공유 비용이 더 큽니다

  3. 느려진 원인 2: 언마운트 정리 누락 → 메모리 누적. 하위 앱을 전환할 때 타이머·이벤트 리스너·ResizeObserver·WebSocket·전역 변수를 해제하지 않으면 반년간 그대로 쌓입니다. 각 하위 앱은 명확한 unmount 계약을 구현해야 하고, 셸은 전환 시 반드시 호출해야 합니다. 샌드박스가 전역 변경을 추적해 자동 복원해 주는 구현(qiankun의 프록시 샌드박스 등)을 쓰면 안전망이 생기지만, 샌드박스 자체도 프록시 가로채기 비용이 있습니다.

  4. 느려진 원인 3: 전환 시점의 리소스 폭주. 전환 때 번들을 처음부터 받으니 백화면이 보입니다. 해법:

    • 유휴 시간 프리로드: 셸이 사용자 권한·이용 패턴 기준으로 다음 하위 앱 번들을 prefetch
    • 단 전부 프리로드하면 초기 로딩이 망가집니다 — 상위 1~2개만
    • 동시 요청 수 제한, 하위 앱 로드 우선순위 관리
    • 전환 중 스켈레톤/프로그레시브 표시

  5. 분할 입도 — 질문의 핵심.

    • 시스템 단위(독립 팀·독립 배포 주기·기술 스택 상이) → 마이크로 프론트엔드가 적합
    • 모듈 단위 → 모노레포 + 패키지 분리가 적합
    • 페이지 단위 → 라우트 코드 분할로 충분. 여기서 마이크로 프론트엔드를 쓰면 손해만 봅니다
    • "일단 잘게 쪼개자"가 이 사고의 원인입니다. 콘웨이 법칙대로 조직 경계에 맞춰 쪼개는 게 기준입니다
    • 전역 모달·알림·권한 컨텍스트 같은 횡단 UI는 하위 앱으로 내리지 말고 셸이 소유합니다

  6. 스타일 격리. CSS Modules·BEM 규약은 하위 앱 간 충돌을 구조적으로 막아 주지 않습니다. 런타임 스코프 주입이나 Shadow DOM을 쓰는데, Shadow DOM은 서드파티 UI 라이브러리의 포털(모달·툴팁)과 자주 충돌하므로 미리 검증이 필요합니다.

  7. 측정과 운영. 하위 앱별 로드 시간·메모리 점유·백화면 시간을 분리 계측하고, 하나가 실패해도 전체가 죽지 않게 앱 단위 폴백을 둡니다. 개선 효과는 "전환 시간 x→y, 메모리 증가 기울기 제거"처럼 수치로 말합니다.

20. React/Vue/Angular 앱 간 상태 공유
7664540949209510779

질문 — 셸은 React, 하위 앱 A는 Vue, B는 Angular입니다. 이들이 로그인 상태와 장바구니 데이터를 공유해야 합니다. 통신 방안을 설계하세요. 타입 안전성은? 순환 의존은? 한 앱이 죽으면 다른 앱 상태에 영향이 있나요?

지원자 답변 — "Vuex와 React Context를 이벤트 버스로 연결하겠습니다." → 타입 안전성·순환 의존·장애 격리에서 막힘.

정답

  1. 원칙: 최소 결합 + 프레임워크 중립. 특정 프레임워크의 상태 관리를 공유 수단으로 쓰면 그 순간 프레임워크 중립성이 깨집니다. 공유 계층은 순수 JS(또는 TS)로만 작성해야 합니다.

  2. 방안을 결합도 순으로 제시합니다.

    방안 결합도 적합한 데이터 한계
    URL (query/hash) 가장 낮음 선택된 탭, 필터, ID 작은 원시값만, 공개됨
    CustomEvent 발행/구독 낮음 단순 알림("로그아웃됨") 상태가 아니라 이벤트, 늦게 붙은 앱은 과거 이벤트를 못 봄
    셸이 소유한 스토어 + 액션 중간 로그인 정보, 장바구니 셸에 의존
    프레임워크 제공 채널 (qiankun initGlobalState, single-spa 공유 모듈) 중간 위와 동일 프레임워크 종속

    장바구니·로그인 상태처럼 "현재 값"이 필요한 데이터는 이벤트가 아니라 스토어가 맞습니다. 이벤트만 쓰면 나중에 마운트된 앱이 현재 상태를 알 수 없습니다.

  3. 권장 설계 — 셸 소유 스토어 + 단방향 쓰기.

    • 셸이 프레임워크 비의존 스토어(작은 옵저버블)를 만들어 getState(), subscribe(fn), 그리고 명시적 액션(login(), addToCart())만 노출합니다
    • 하위 앱은 직접 state를 수정할 수 없고 액션만 호출합니다. 변경 경로가 하나라 추적·감사·디버깅이 가능합니다
    • 각 하위 앱은 subscribe로 받은 값을 자기 프레임워크 상태로 얇게 어댑트합니다 (Vue는 ref로, React는 useSyncExternalStore로, Angular는 BehaviorSubject로)
    • useSyncExternalStore가 React 쪽 정석입니다 — 동시 렌더링에서 tearing을 막아 줍니다 (→ 3번 항목)

  4. 타입 안전성 — 질문의 추궁 포인트. 공유 계약을 독립 패키지(@acme/shell-contract)로 만들어 타입 정의와 이벤트 이름 상수를 한곳에서 관리하고, 모든 앱이 이 패키지를 devDependency로 참조합니다. 런타임에는 타입이 사라지므로 경계에서 스키마 검증(zod 등)을 한 번 겁니다. 이벤트 이름을 문자열 리터럴로 흩뿌리는 게 가장 흔한 실패 원인입니다. 계약 패키지는 버전을 매겨 호환성을 관리합니다.

  5. 순환 의존 방지. 하위 앱끼리 직접 import하거나 서로의 함수를 호출하는 것을 금지합니다. 모든 교신은 셸(또는 메시지 버스)을 경유합니다. 이게 순환 의존을 구조적으로 불가능하게 만들고, 동시에 모니터링 지점을 한곳으로 모아 줍니다.

  6. 장애 격리 — 추궁 포인트 2.

    • 상태의 단일 소유자가 셸이므로 하위 앱 A가 죽어도 상태 자체는 보존됩니다. 반대로 상태를 하위 앱이 들고 있었다면 그 앱과 함께 사라집니다 — 이것이 셸 소유 설계의 가장 중요한 이유입니다
    • 하위 앱 마운트 실패는 에러 바운더리로 감싸 해당 영역만 폴백 UI로 대체하고 나머지는 계속 동작하게 합니다
    • 구독 콜백은 try/catch로 감싸 한 앱의 예외가 다른 구독자에게 전파되지 않게 합니다
    • 앱 언마운트 시 구독 해제를 보장합니다 (안 하면 → 19번의 메모리 누적)

  7. 민감 데이터. 로그인 토큰은 공유 스토어에 평문으로 두지 않고, 셸이 보관하고 하위 앱에는 "인증된 요청을 보내는 함수"만 노출하는 쪽이 안전합니다. localStorage 공유는 XSS 시 전부 노출됩니다.

이 질문의 본질: 분산 시스템 사고를 UI에 적용할 수 있는지. 마이크로 프론트엔드는 분산 UI 시스템이고, 통신 설계가 전체 가용성을 결정합니다.

21. 권한·탭·캐시가 얽힌 관리자 라우팅 설계
7656758629861705914

질문 — 다중 역할 + 버튼 단위 권한 + 다중 탭(탭 전환 시 폼/필터 상태 유지) + 로그인 만료 + 동적 메뉴를 모두 지원하는 라우팅 아키텍처를 설계하세요.

지원자 답변 — "Vue Router에 가드 걸고 <keep-alive> 쓰면 됩니다." → 동적 라우트를 프론트에 하드코딩할지 서버가 내려줄지, 탭 누적으로 인한 메모리 초과 제어, 권한 갱신 후 재적용, 탭 간 동기화에서 전부 막힘.

정답

  1. 라우트를 두 층으로 나눕니다.

    • 정적 라우트: 로그인, 404, 403, 레이아웃 셸 — 빌드 시 고정
    • 동적 라우트: 권한에 따라 런타임에 등록
    • 동적 라우트는 반드시 서버가 내려주는 권한 코드로 생성합니다. 프론트에 역할별 라우트를 하드코딩하면 역할 추가마다 배포가 필요하고, 무엇보다 클라이언트 코드를 조작해 우회할 수 있어 보안이 아닙니다. 프론트 권한 제어는 UX이고, 실제 인가는 서버 API가 검증합니다 — 이 구분을 명시하는 게 중요합니다

  2. 권한 모델. 서버는 권한 코드 목록(예: order:list, order:export)을 주고, 프론트는 라우트 meta.permission과 매칭해 라우트 트리를 조립합니다. 버튼 단위는 디렉티브/컴포넌트(v-permission 또는 <Can code="order:export">)로 처리합니다. 권한이 없으면 숨기는 것과 비활성화하는 것의 UX 차이를 정해 둡니다.

  3. 권한 변경 시 재적용. 역할이 바뀌거나 재로그인하면 이전에 등록한 동적 라우트를 제거하고 다시 등록해야 합니다. Vue Router 4의 addRoute()가 돌려주는 제거 함수를 보관하거나, 라우터를 재생성합니다. 이걸 안 하면 이전 역할의 라우트가 남아 접근 가능한 상태가 됩니다 — 실제로 자주 나오는 보안 사고입니다. 동시에 메뉴·탭·캐시를 함께 초기화합니다.

  4. 탭 + 캐시 연동 — 가장 까다로운 부분.

    • 탭 레지스트리: { 라우트 경로, 쿼리, 제목, 캐시 키 } 목록을 전역 상태로 관리
    • 캐시 키 설계: 같은 라우트를 다른 파라미터로 열면 독립 탭·독립 캐시여야 합니다(주문 #1과 #2). Vue는 <keep-alive :include>에 컴포넌트 이름을 넣는 구조라 파라미터별 분리가 어려우므로, 동적 컴포넌트 이름이나 key를 캐시 키로 쓰는 우회가 필요합니다. React는 라우트별 상태를 외부 스토어에 키로 보관하는 쪽이 자연스럽습니다
    • 메모리 상한: 최대 탭 수(예: 10~15)를 정하고 LRU로 가장 오래 쓰지 않은 탭을 자동 해제합니다. 상한이 없으면 하루 종일 쓰는 관리자 화면에서 메모리가 선형 증가합니다
    • 탭 닫기 = 캐시 해제: 탭을 닫으면 반드시 캐시에서 제거하고, 그 화면의 타이머·폴링·구독을 정리합니다
    • 비활성 탭의 폴링 중지: 보이지 않는 탭의 테이블 자동 갱신은 멈춥니다. 이것 하나로 CPU 사용량이 크게 떨어집니다
    • 같은 메뉴 재클릭: 새 탭을 만들지 말고 기존 탭으로 포커스 이동

  5. 로그인 만료·예외 처리.

    • 401 → 토큰 갱신 시도 → 실패 시 캐시·탭·라우트 전부 초기화하고 로그인으로. 갱신 중 들어온 동시 요청은 큐에 모아 한 번만 갱신합니다(그러지 않으면 갱신 요청이 폭주)
    • 403 → 권한 없음 페이지. 메뉴에서도 제거
    • 동적 import 실패(배포로 청크가 사라짐) → 캐시 정리 후 리로드 (→ 26번)
    • 알 수 없는 경로 → 404. 동적 라우트 등록 전에 와일드카드 404를 등록하면 모든 경로가 404로 빨려 들어갑니다 — 흔한 함정

  6. 다중 탭(브라우저 탭) 동기화. 한 탭에서 로그아웃하면 다른 탭도 반영되어야 합니다. storage 이벤트나 BroadcastChannel로 로그아웃·권한 변경을 전파합니다.

  7. 로딩 전략. 정적 라우트는 즉시, 업무 라우트는 lazy/동적 import. 자주 쓰는 상위 메뉴는 유휴 시 프리페치.

22. 크로스 플랫폼 프레임워크를 처음부터 설계
76504462222358348097660481003748670065

질문 — 미니프로그램(위챗), H5, 앱(WebView)을 동시에 지원하는 크로스 플랫폼 프레임워크를 처음부터 설계하세요. 코드 변환과 런타임 적응을 어떻게 하나요?

지원자 답변 — "환경 판별을 여러 개 쓰고 조건부 컴파일하겠습니다." → 프레임워크를 쓸 줄은 알지만 만드는 설계를 모름.

정답

  1. 먼저 조건부 컴파일만으로는 안 되는 이유를 말합니다. 페이지마다 if (platform === 'mp')를 흩뿌리면 ① 코드가 분기 폭발로 읽을 수 없게 되고 ② 로직 하나를 바꿀 때 세 군데를 수정해야 하고 ③ 플랫폼별 동작 불일치 버그가 구조적으로 발생합니다. 프레임워크의 역할은 차이를 한곳에 모아 가두는 것입니다.

  2. 플랫폼 차이의 근원 — 이걸 모르면 설계가 안 나옵니다.

    • 미니프로그램: 로직 레이어(JS 엔진)와 렌더 레이어(WebView)가 분리된 2스레드 구조. 둘 사이는 비동기 메시지로만 통신하고, 표준 DOM API가 없습니다. 그래서 setData 호출 비용이 크고 동기적 DOM 조작이 불가능합니다
    • H5: 표준 DOM, 단일 메인 스레드
    • 앱 WebView: 표준 DOM + 네이티브 브리지(비동기) 이 차이 때문에 "컴파일만으로는 해결 안 되고 런타임이 필요"합니다.

  3. 컴파일 타임 계층 — 정적인 것을 변환

    • AST 기반 변환: 통일된 DSL(Vue/React 문법)을 파싱해 AST로 만들고, 타깃별로 생성합니다. 미니프로그램은 WXML+WXSS+JS, H5는 표준 HTML+CSS+JS
    • 템플릿/태그 매핑: 커스텀 태그를 각 플랫폼 네이티브 태그로. 이벤트 바인딩 문법도 매핑
    • 스타일 단위 변환: rpx ↔ px ↔ vw 자동 환산, 스타일 스코프 격리 방식 변환 (미니프로그램은 컴포넌트 스타일 격리가 기본)
    • 라우트/분팩: 하나의 라우트 설정에서 플랫폼별 라우트 테이블과 분팩 구성을 생성
    • 조건부 컴파일은 여기서 "예외 처리용"으로만 남깁니다 (파일명 접미사나 전용 주석 문법으로 제한)

  4. 런타임 계층 — 동적인 것을 흡수. 프레임워크의 본체

    • 통일 API 어댑터: 업무 코드는 request(), navigate(), toast() 같은 단일 인터페이스만 호출하고, 어댑터가 wx.* / fetch / 네이티브 브리지로 분배합니다. 플랫폼 추가 = 어댑터 하나 추가
    • DOM 심(shim): 미니프로그램에는 DOM이 없으므로, 가상 DOM 트리를 런타임이 유지하고 변경분만 setData로 보내는 경량 DOM 구현을 제공합니다 (Taro 3·Remax가 이 방식). 배치와 diff 최소화가 성능의 핵심
    • 이벤트 시스템 통일: 버블링·캡처·터치 이벤트 동작이 플랫폼마다 달라, 런타임이 합성 이벤트로 추상화합니다
    • 생명주기 매핑: 미니프로그램의 onLoad/onShow/onHide, H5의 라우트 훅, WebView 컨테이너 생명주기를 단일 훅 집합으로 모으고 호출 시점을 정렬합니다
    • 컴포넌트 런타임: 커스텀 컴포넌트를 플랫폼 네이티브 컴포넌트 체계에 등록

  5. 격리와 네이티브 브리지

    • 플러그인/서드파티 코드용 샌드박스(전역 오염 방지)
    • 네이티브 통신 브리지: 앱은 JSBridge, 미니프로그램은 전용 API, H5는 폴백. 통신은 모두 비동기라는 전제로 API를 설계해야 합니다 (동기 API를 노출하면 플랫폼 하나에서 구현 불가)

  6. 폴백·성능·운영

    • 능력 탐지 후 강등: API가 없는 플랫폼에서는 범용 구현으로 대체하고 콘솔 경고. 조용히 실패하면 디버깅 불가
    • 컴파일 타임에 쓰지 않는 플랫폼 분기 제거(dead code elimination)로 런타임 판별 비용과 번들 크기 축소
    • 번들 계층화: 공통 런타임 / 업무 코드 / 플랫폼 어댑터를 분리해 필요한 것만 로드. 미니프로그램은 패키지 크기 제한이 엄격하므로 중요
    • 어댑터 계층에서 에러·성능 로그 포맷을 통일해 플랫폼별로 흩어진 로그를 한 대시보드에서 봅니다
    • 저버전 미니프로그램 호환: 문법·API 폴리필과 능력 체크

이 질문이 선별하는 것: Uni-app/Taro를 써 봤는지가 아니라, 컴파일 타임과 런타임이 각각 어떤 문제를 푸는지 구분하고 계층으로 나눌 수 있는지입니다.

23. 서버가 내려주는 원격 컴포넌트 동적 로딩
7672352344453048953

질문 — 운영 백오피스에서 마케팅 팝업을 재배포 없이 교체해야 합니다. 서버가 컴포넌트 코드 문자열을 내려주면 런타임에 로드하는 구조를 어떻게 구현하나요? 버전 불일치, 스타일 오염, 정리되지 않은 전역 리스너, 그리고 악성 코드가 섞여 있으면 어떻게 대응하나요?

지원자 답변 — "defineAsyncComponent + 동적 import, 문자열이면 new Function이나 런타임 컴파일." → 버전 호환·격리·보안 추궁에서 전부 막힘.

정답

⚠️ 먼저 전제를 바로잡아야 합니다. 영상은 "2026년 표준 관행", "백엔드 대형 모델이 어댑터를 자동 생성", "행위 지표로 자동 차단" 같은 내용을 단정적으로 제시하는데, 이는 검증된 업계 표준이 아닌 추측·마케팅 서술입니다. 실제 면접에서는 아래처럼 보안 우선 순서로 답하는 게 맞습니다.

  1. 가장 좋은 답은 "임의 코드를 실행하지 않는 설계"입니다. 마케팅 팝업 교체가 목적이라면 코드가 아니라 설정(JSON) 기반 렌더링이 정답입니다. 미리 검증된 컴포넌트 집합을 번들에 포함하고, 서버는 "어떤 컴포넌트를 어떤 props로 조합할지"만 내려줍니다. 임의 코드 실행 경로가 없어 보안 문제 자체가 사라지고, 버전 호환 문제도 없습니다. 면접에서는 이 대안을 먼저 제시한 뒤, 그래도 코드를 내려받아야 한다면 아래 조치를 쌓는다고 답하는 게 가장 높은 평가를 받습니다.

  2. 그래도 원격 코드를 로드해야 한다면 — 로드 방식.

    • new Function/eval로 코드 문자열을 실행하는 방식은 피합니다. CSP(script-src에 unsafe-eval 필요)를 무력화해야 하고, 전체 앱의 보안 수준을 떨어뜨립니다
    • Module Federation이나 ES Module 동적 import로 빌드 산출물을 불러오는 쪽이 정석입니다. 코드가 빌드 파이프라인을 거치므로 검증·서명·버전 관리가 가능합니다
    • 원격 번들은 서브리소스 무결성(SRI) 과 서명 검증으로 변조를 차단합니다

  3. 버전 계약 — 질문의 첫 추궁.

    • 의존성 외부화(externals) + 주입: 원격 컴포넌트는 Vue/React·UI 라이브러리를 번들에 포함하지 않고 외부 의존으로 표시합니다. 셸이 로드 시 자기 인스턴스를 주입합니다. 프레임워크 인스턴스가 하나로 유지돼 훅·컨텍스트가 정상 동작합니다
    • 호환 범위를 계약으로 명시: Module Federation의 shared + requiredVersion으로 허용 범위를 선언하고, 벗어나면 로드를 거부하고 폴백합니다. 조용히 실행해서 런타임에 깨지는 것보다 낫습니다
    • 원격 컴포넌트가 셸에 없는 신규 API를 쓰면 — 자동 어댑터 생성 같은 마법을 기대하지 말고, 매니페스트에 요구 버전을 선언하게 하고 셸이 사전에 검증하는 게 현실적인 설계입니다

  4. 스타일 격리.

    • Shadow DOM이 가장 강력합니다. 원격 컴포넌트의 스타일이 바깥으로 새지 않고 셸 스타일도 안으로 들어가지 않습니다. 필요한 부분만 ::part()로 커스터마이즈 허용
    • 단 Shadow DOM은 포털(모달·툴팁·드롭다운)과 폰트·전역 토큰 상속에서 자주 문제를 일으키므로 사전 검증이 필요합니다. 대안은 빌드 시 스코프 접두사 주입

  5. 부수 효과 정리. 원격 컴포넌트가 타이머·리스너·옵저버를 남기면 메모리 누수가 됩니다.

    • 컴포넌트에 정리를 맡기지 말고 셸이 회수하는 구조로 만듭니다. 샌드박스가 setTimeout/addEventListener/MutationObserver를 프록시로 감싸 등록 내역을 기록하고, 언마운트 시 일괄 해제합니다
    • AbortController 하나를 컴포넌트에 주입해 모든 비동기·리스너를 그 signal에 묶게 하는 방식이 더 단순하고 표준적입니다

  6. 보안 — 핵심 추궁("악성 코드라면?"). 원격 코드는 신뢰할 수 없는 입력으로 취급합니다.

    • 가장 확실한 격리는 샌드박스 iframe입니다. <iframe sandbox="allow-scripts">(same-origin 미허용)에 넣으면 별도 오리진·별도 실행 컨텍스트가 되어 셸의 DOM·쿠키·스토리지에 접근할 수 없습니다. 통신은 postMessage로만. 비용은 통신 오버헤드와 레이아웃 제약이지만, 보안이 요구되면 이게 정답입니다
    • Proxy 기반 JS 샌드박스는 격리가 아니라 완화입니다. 프로토타입 체인, 생성자 우회([].constructor.constructor), import() 등으로 탈출 경로가 계속 발견되므로, "악성 코드를 막는다"고 주장하면 안 됩니다
    • CSP: script-src로 허용 출처를 제한, connect-src로 통신 대상 제한, frame-ancestors/form-action으로 리다이렉트·폼 전송 차단. 영상이 예로 든 document.location 변조는 CSP와 샌드박스 iframe으로 차단합니다
    • 정적 검사: 배포 파이프라인에서 위험 패턴(eval, 동적 생성자, 허용 외 도메인 통신)을 스캔해 게시 전에 거부합니다. 런타임 탐지보다 앞단에서 막는 게 효과적입니다
    • 최소 권한: 컴포넌트가 필요한 능력을 매니페스트로 선언하고, 셸은 선언된 것만 주입합니다 (스토리지 접근, 특정 API 호출 등)
    • 운영 안전장치: 원격 컴포넌트별로 로드 실패·에러율을 집계해 임계치 초과 시 자동 비활성화 + 플레이스홀더 표시. 롤백 경로를 반드시 둡니다

  7. 정리. 이 주제의 올바른 답은 "로드 기술"이 아니라 신뢰 경계를 어디에 그을지입니다. 우선순위: ① 설정 기반으로 코드 실행을 없앤다 → ② 불가피하면 빌드된 모듈 + 버전 계약 + 서명 → ③ 보안이 중요하면 샌드박스 iframe + CSP → ④ 운영에서 자동 차단·롤백.

24. TypeScript와 JavaScript의 차이
7686800241719179451

질문 — TS와 JS의 본질적 차이는? 프로젝트에 TS를 왜 쓰나요? 타입 시스템이란 무엇이고 컴파일 타임과 런타임의 차이는? 인터페이스와 제네릭은 왜 쓰죠?

지원자 답변 — "타입이 붙은 JS. 쓰기가 좀 번거롭습니다." → 타입 시스템의 의미와 적용 기준에서 막힘.

정답

  1. TS는 JS의 상위집합(superset)이고, 최종적으로 JS로 컴파일됩니다. 유효한 JS는 모두 유효한 TS입니다. 브라우저·Node는 TS를 직접 실행하지 않습니다(Node 22+ 와 Deno가 타입 제거만 수행하는 실행을 지원하지만, 타입 검사는 별도 과정입니다).

  2. 가장 중요한 한 가지 — 타입은 런타임에 존재하지 않습니다. TS 타입은 컴파일 시 완전히 지워집니다(type erasure). 실무적 함의:

    • API 응답이 선언한 타입과 다르면 TS는 아무것도 막아 주지 않습니다. 컴파일은 통과하고 런타임에 터집니다
    • 그래서 외부 경계(API 응답, URL 쿼리, localStorage, 폼 입력)에서는 런타임 검증이 필요합니다 — zod/valibot 같은 스키마 검증으로 파싱하고, 그 결과에서 타입을 추론해 쓰는 패턴이 정석입니다
    • as(타입 단언)는 "컴파일러에게 믿으라고 말하는 것"일 뿐 검증이 아닙니다. 남용이 TS 프로젝트가 안전하지 않게 되는 가장 큰 경로입니다
    • 이 점을 말할 수 있으면 "TS를 써 봤다"와 "TS를 이해한다"가 갈립니다

  3. 동적 타입 vs 정적 타입. JS는 런타임에 타입이 결정되어 암묵적 변환('1' + 1 === '11')과 undefined is not a function 류의 오류가 실행 중에 발견됩니다. TS는 작성·빌드 시점에 검출합니다. 버그를 발견하는 시점이 왼쪽으로 이동하는 것이 핵심 가치입니다.

  4. TS의 구조적 타이핑(structural typing). TS는 이름이 아니라 형태로 호환성을 판단합니다. 같은 모양이면 같은 타입으로 취급합니다(Java의 명목적 타이핑과 다름). 이 때문에 ID 종류를 구분하려면 브랜드 타입 같은 기법이 필요합니다.

  5. TS가 제공하는 추가 문법 능력.

    • interface / type — 객체 형태 계약. interface는 선언 병합(declaration merging)이 되고 type은 유니온·조건부 타입 등 더 넓은 표현이 가능합니다
    • 제네릭 — 타입을 매개변수화해 재사용성과 타입 안전성을 동시에 확보 (function first<T>(arr: T[]): T | undefined). API 래퍼·상태 관리·컴포넌트 props에서 핵심
    • 유니온/인터섹션, 리터럴 타입, 판별 유니온(discriminated union) — 상태 머신 모델링에 매우 유용 ({ status: 'loading' } | { status: 'success', data: T })
    • 타입 가드와 satisfies, 유틸리티 타입(Partial, Pick, Omit, Record, ReturnType)
    • enum과 데코레이터는 TS 고유 문법이지만, enum은 런타임 코드를 생성해 as const 객체로 대체하는 흐름이 있습니다

  6. 실무적 가치 — "번거롭다"에 대한 반박.

    • IDE 지원: 자동완성·정확한 리팩터링·참조 찾기. 코드베이스가 커질수록 이 이득이 지배적입니다
    • 문서화: 타입 자체가 항상 최신인 계약 문서
    • 리팩터링 안전성: 필드 이름을 바꾸면 영향받는 모든 지점이 즉시 드러납니다. JS에서는 문자열 검색에 의존해야 합니다
    • 팀 협업: 함수의 입출력 계약이 명시되어 구두 합의가 필요 없습니다

  7. 적용 기준.

    • 짧은 스크립트·프로토타입·일회성 작업 → JS로 충분
    • 중대형·다인 협업·장기 유지보수·라이브러리/프레임워크 개발 → TS
    • 점진 도입: allowJs로 공존 → 파일 단위 전환 → strict 단계적 활성화. strict: true(특히 strictNullChecks)를 켜지 않으면 TS의 이점 대부분을 잃습니다. noUncheckedIndexedAccess도 켜 두면 배열 접근 실수를 많이 잡습니다
    • any 사용은 ESLint로 금지·경고. unknown으로 받고 좁혀 나가는 습관
25. 의존성 버전 충돌 근본 해결
7687926118171065957

질문 — 대형 관리자 프로젝트에서 로컬은 정상인데 빌드·배포하면 컴파일 실패, 새 패키지를 설치하면 기존 기능이 깨지고 스타일이 어긋나고 백화면까지 납니다. 버전을 고정했는데도 충돌이 반복됩니다. "로컬은 되는데 빌드는 깨짐"을 설치·버전 고정·엔지니어링 전반에서 어떻게 근본 해결하나요?

지원자 답변 — "node_modules 지우고 재설치, 버전 번호 고정." → 중첩 의존성·패키지 매니저 차이·유령 의존성에서 막힘.

정답

  1. 원인을 먼저 분리합니다 — "로컬은 되는데 빌드는 깨짐"의 전형적 범인.

    • lockfile이 커밋되지 않았거나 CI가 무시함. 로컬은 몇 달 전 설치된 트리를, CI는 방금 해석한 최신 트리를 씁니다. 이게 1번 원인입니다
    • 유령 의존성(phantom dependency): package.json에 없는 패키지를 import했는데, 다른 패키지의 전이 의존으로 node_modules 평탄화 덕분에 로컬에서는 우연히 해결됩니다. 트리가 조금 달라지면 CI에서 사라집니다
    • 중첩된 다중 버전: package.json에서 버전을 고정해도 하위 의존성이 요구하는 버전은 고정되지 않습니다. "고정했는데 충돌"의 답이 여기입니다 (→ 18번과 같은 뿌리)
    • 패키지 매니저 혼용: npm·yarn·pnpm의 해석 규칙과 평탄화 방식이 달라 lockfile이 2종 이상 존재하면 사람마다 다른 트리를 갖습니다
    • 플랫폼 차이: 네이티브 바이너리(sass, esbuild, sharp)의 OS·아키텍처별 산출물, 대소문자 구분 파일시스템(macOS는 비구분, Linux는 구분 → import 경로 대소문자 오류가 CI에서만 발생)

  2. 1층: 설치 규범 — 결정론적 설치를 만든다.

    • lockfile을 반드시 커밋하고, CI는 npm ci / pnpm install --frozen-lockfile / yarn install --immutable로 설치합니다. 이 플래그가 없으면 lockfile이 조용히 갱신되어 재현성이 사라집니다
    • 패키지 매니저를 하나로 통일합니다. package.json의 packageManager 필드 + Corepack으로 버전까지 고정하고, 다른 lockfile은 삭제 후 .gitignore가 아니라 CI 검사로 금지합니다
    • Node 버전 고정: .nvmrc/engines + CI에서 동일 버전 사용
    • 직접 쓰는 모든 패키지를 package.json에 명시합니다 (유령 의존성 제거)
    • 버전 범위: 애플리케이션은 보수적으로(~ 또는 정확한 버전) + Renovate/Dependabot으로 의도적인 업데이트 PR을 받습니다. "자동으로 올라가게 두고 안 깨지길 바라는" 상태가 가장 위험합니다

  3. 2층: 충돌 해소 — 다중 버전 자체를 줄인다.

    • npm ls <pkg> / pnpm why <pkg> 로 실제 트리를 확인합니다 (추측 금지)
    • overrides/resolutions로 하위 의존 버전을 통일합니다. 단 semver 호환 범위 내에서만 — 메이저가 다르면 강제 통합이 런타임 에러를 만듭니다 (→ 18번)
    • peerDependencies를 정확히 다룹니다. UI 라이브러리가 요구하는 프레임워크 버전과 프로젝트 버전이 어긋나면 컴파일 또는 런타임에서 깨집니다. npm 7+ 는 peer 충돌 시 설치를 거부하는데, --legacy-peer-deps로 억지로 넘기는 것이 "로컬은 되는데 빌드는 깨짐"의 또 다른 흔한 입구입니다. 경고를 무시하지 말고 버전을 맞추세요
    • React/Vue 같은 프레임워크는 인스턴스가 반드시 하나여야 합니다. 두 벌이면 훅 에러·컨텍스트 미동작이 발생합니다. 모노레포라면 resolve.dedupe(Vite)나 webpack resolve.alias로 단일화합니다
    • 불필요·중복 라이브러리 정리(depcheck), 전이 의존 깊이를 줄이기

  4. 3층: 엔지니어링 폴백 — 환경 차이를 구조적으로 제거.

    • pnpm의 엄격한 node_modules 구조는 유령 의존성을 구조적으로 차단합니다. 이 문제를 반복적으로 겪는 팀이 pnpm으로 옮기는 주된 이유입니다
    • CI는 항상 깨끗한 환경에서 설치 (캐시를 쓰더라도 lockfile 해시 기준으로 무효화)
    • 로컬 환경도 컨테이너/devcontainer로 통일하면 OS 차이에서 오는 문제가 사라집니다
    • 정기 점검 루틴: 보안 취약점(npm audit), 오래된 의존성 일괄 업데이트 창구, 메이저 업그레이드는 별도 PR로 분리
    • 빌드 산출물을 로컬에서도 한 번 돌려 보는 CI 동일 명령(npm run build)을 pre-push 훅이나 PR 필수 체크로 둡니다

요지: "재설치 + 버전 고정"은 증상 완화입니다. 근본 해결은 ① lockfile 기반 결정론적 설치 ② 명시적 의존성 ③ 하위 의존 버전 통일(호환 범위 내) ④ 로컬=CI 환경 동일화 네 가지입니다.

26. 배포 후 사용자에게 새로고침 알리기
7701289842043211129

질문 — 프론트엔드를 재배포한 뒤 사용자에게 어떻게 새로고침을 알리나요? 사용자가 긴 폼을 작성 중이면? 구버전 화면에서 버튼을 눌렀는데 API 스펙이 바뀌어 에러가 나면? 신·구 리소스가 맞지 않으면 어떻게 폴백하나요?

지원자 답변 — "버전 번호를 비교해서 갱신이 감지되면 확인 창을 띄워 새로고침." → 작성 중 데이터 유실, API 비호환, 리소스 불일치 대응에서 막힘.

정답

  1. 캐시 전략이 먼저입니다 — 이게 틀리면 알림을 아무리 잘 만들어도 무용지물.

    • 엔트리 HTML: Cache-Control: no-cache (매번 재검증). 이게 장기 캐시되면 새 배포가 사용자에게 절대 도달하지 않습니다
    • 해시 파일명이 붙은 JS/CSS: max-age=31536000, immutable (영구 캐시)
    • 이 조합이 뒤바뀐 것이 "배포했는데 사용자가 구버전을 본다"의 가장 흔한 원인입니다. 영상도 이 점을 정확히 지적하는데, 실제로 가장 중요한 항목입니다

  2. 1층: 감지 — 폴링만으로는 부족합니다.

    • 빌드 시 버전 매니페스트(/version.json에 빌드 해시/타임스탬프)를 생성하고, 이 파일은 캐시하지 않습니다
    • 감지 트리거를 조합합니다:
      • 저빈도 폴링(예: 5~10분)을 기본으로
      • visibilitychange — 탭으로 돌아올 때 즉시 확인 (가장 효과적인 트리거)
      • online — 네트워크 재연결 시
      • 라우트 전환 시 (SPA에서 자연스러운 체크포인트)
    • 원칙: 빈도를 높이는 게 아니라 결정적 순간을 놓치지 않는 것. 1초마다 폴링하는 것보다 탭 복귀 시 1회 확인이 낫습니다
    • 실무 대안: Service Worker를 쓰면 registration.update() + updatefound 이벤트로 표준적으로 처리할 수 있습니다

  3. 2층: 알림 — 상황에 따라 차등 적용. 강제 새로고침은 재앙입니다.

    • 미저장 입력이 없는 화면(대시보드, 목록, 조회) → 조용히 자동 리로드하거나 다음 라우트 전환 시 적용
    • 입력 중인 화면(폼, 에디터, 업로드) → 절대 중단시키지 않습니다. 비차단 토스트/배너로 "새 버전이 있습니다 — 지금 갱신 / 나중에" 선택권을 줍니다
      • 추가로 입력 내용을 sessionStorage에 자동 저장해 두면 사용자가 "지금 갱신"을 눌러도 데이터가 복원됩니다. 이게 진짜 해법입니다
    • "나중에"를 영구 침묵으로 만들지 않습니다 — 라우트 전환이나 다음 감지 시 다시 알립니다
    • 강제 vs 선택 구분: API 계약 비호환이나 보안 수정은 강제 플래그를 매니페스트에 담아 즉시 갱신을 요구합니다. 일반 UI 수정은 선택
    • beforeunload는 브라우저가 커스텀 메시지를 막으므로 UX 수단으로 의존하지 않습니다

  4. 3층: 리소스 폴백 — "알림을 놓친 사용자"를 구제하는 계층. 알림에 의존하면 반드시 구멍이 생깁니다.

    • 동적 import 실패 처리: 구버전 HTML이 들고 있는 청크 파일명이 새 배포로 사라져 404가 나면 화면이 백지가 됩니다. 라우트/컴포넌트 lazy 로드를 감싸서 로드 실패를 잡고 → 캐시 정리 → 강제 리로드합니다. 무한 리로드 루프를 막기 위해 세션당 1~2회로 제한합니다
    const retryKey = 'chunk-reload-count';
function lazyWithReload(loader) {
  return () => loader().catch((err) => {
    const n = Number(sessionStorage.getItem(retryKey) ?? 0);
    if (n < 1) {                       // 1회만 재시도 — 루프 방지
      sessionStorage.setItem(retryKey, String(n + 1));
      window.location.reload();
    }
    throw err;                         // 그 이상이면 에러 UI로
  });
}
    • 구버전 유지 기간: 배포 시 이전 버전 청크를 즉시 지우지 말고 일정 기간(보통 며칠) 보존하면 이 문제의 발생 빈도 자체가 크게 줄어듭니다. CDN 비용 대비 가장 효율적인 조치입니다
    • API 버전 불일치: 요청 헤더에 프론트엔드 빌드 버전을 실어 보내고, 서버가 비호환이면 전용 에러 코드를 반환합니다. 프론트는 그 코드를 받으면 강제 갱신 안내를 띄웁니다. 일반 에러 메시지로 묻히게 하지 않는 게 포인트
    • 다중 탭: BroadcastChannel로 갱신 사실을 전파해 모든 탭이 일관된 상태가 되게 합니다

  5. 정리. 핵심은 "확인 창을 띄울지"가 아니라 ① 캐시 헤더를 올바르게 구성 ② 결정적 순간에 감지 ③ 사용자 작업 상태에 따라 차등 알림 ④ 알림이 실패해도 리소스 폴백으로 복구 네 단계의 폐루프를 만드는 것입니다. 사용자가 새로고침하지 않는 것이 문제가 아니라, 새로고침 후에도 구버전이거나 백지가 되는 것이 진짜 문제입니다.

27. 線上 JS 에러를 원본 소스 위치로 추적
7701623734822975610

질문 — 운영 환경에서 JS 에러가 났습니다. 어떻게 원본 소스 위치를 빠르게 찾나요? 코드는 압축·난독화되어 변수가 전부 a, b, c입니다. 소스맵의 원리는? 운영에 소스맵을 그대로 켜도 되나요? 위험은? 에러 수집 플랫폼에 들어온 난독화된 스택을 어떻게 복원하죠?

지원자 답변 — "콘솔에서 에러 메시지와 스택을 봅니다." → 압축 후 스택을 복원하는 방법, 소스맵 원리와 보안 위험에서 막힘.

정답

  1. 문제의 원인. 빌드 과정에서 minify·난독화를 거치면 변수·함수명이 축약되고 줄바꿈이 제거됩니다. 브라우저 콘솔에 찍히는 줄·열 번호는 압축된 산출물 기준이라 원본 코드와 전혀 대응되지 않습니다. 번들된 한 줄에 수만 문자가 들어 있으니 줄 번호 자체가 무의미합니다.

  2. 소스맵의 원리. .map 파일은 압축 산출물의 (줄, 열) → 원본 파일의 (파일명, 줄, 열, 식별자명) 매핑을 VLQ Base64로 인코딩해 담은 JSON입니다. 주요 필드는 sources(원본 파일 경로), names(원본 식별자), mappings(실제 매핑 데이터), sourcesContent(원본 코드 전문 — 선택 항목이며 보안상 핵심)입니다. 소스맵이 있으면 난독화된 위치를 원본 위치로 역변환할 수 있습니다.

  3. 환경별 운용 — 질문의 핵심.

    환경 소스맵 방식
    로컬/개발 켠다 eval-source-map 등 빠른 모드. 콘솔에서 바로 원본으로 점프
    운영 공개하지 않는다 hidden-source-map으로 생성 → 에러 모니터링 플랫폼에 업로드 → 배포 산출물에서 삭제
    긴급 대응 로컬 보관 해당 배포 버전의 .map을 사내 저장소에서 꺼내 오프라인 복원
    • hidden-source-map 이 핵심입니다. 소스맵 파일은 생성하지만 JS 파일 끝에 //# sourceMappingURL= 주석을 넣지 않습니다. 브라우저가 찾아갈 경로가 없어 외부에 노출되지 않습니다
    • CI 파이프라인에서 빌드 → 소스맵 업로드 → 산출물에서 .map 삭제 → 배포 순서를 자동화합니다. 수동으로 하면 반드시 언젠가 유출됩니다

  4. 보안 위험 — 추궁 포인트.

    • .map을 CDN에 공개하면 sourcesContent를 통해 프론트엔드 전체 소스가 그대로 노출됩니다. 비즈니스 로직, 내부 API 경로와 파라미터 구조, 미출시 기능 플래그, 주석에 남은 정보까지 전부입니다
    • 흔한 사고 경로: devtool: 'source-map'을 운영에 그대로 두거나, .map을 지우는 단계를 CI에 넣지 않는 것
    • 점검 방법: 배포 후 curl -I https://cdn.example.com/app.abc123.js.map으로 200이 오는지 확인합니다. 이걸 CI 검증 단계로 넣어 두세요
    • ⚠️ 프론트엔드 코드는 어차피 클라이언트에 전달되므로 소스맵이 없어도 역컴파일은 가능합니다. 소스맵 유출은 "어렵게 만들던 장벽을 완전히 없애는 것" 이지 유일한 방어선은 아닙니다. 그래서 애초에 비밀을 프론트엔드 코드에 두지 않는 것(API 키, 내부 엔드포인트 하드코딩 금지)이 더 근본적입니다

  5. 에러 수집 플랫폼 연동 — 실무 흐름.

    • 브라우저에서 window.onerror, unhandledrejection, React ErrorBoundary로 에러를 수집해 스택 + 빌드 버전(release) + 사용자 컨텍스트를 전송합니다
    • 플랫폼(Sentry 등)은 업로드된 소스맵과 release 식별자로 매칭해 스택을 심볼화(symbolication)합니다
    • release/dist 식별자가 일치하지 않으면 복원이 실패합니다. 빌드 해시나 Git 커밋 SHA를 release로 쓰고, 업로드 시와 런타임 전송 시 같은 값을 쓰도록 빌드 변수로 주입합니다. "소스맵을 업로드했는데 복원이 안 된다"의 90%가 이 불일치입니다
    • 소스맵은 배포 버전별로 보관합니다. 롤백한 버전의 에러를 복원해야 할 수 있습니다

  6. 플랫폼 없이 긴급 복원. 해당 버전의 .map과 난독화된 스택 좌표가 있으면 source-map 패키지로 로컬에서 역변환할 수 있습니다.

import { SourceMapConsumer } from 'source-map';
const raw = JSON.parse(await fs.readFile('app.abc123.js.map', 'utf8'));
await SourceMapConsumer.with(raw, null, (consumer) =>
  console.log(consumer.originalPositionFor({ line: 1, column: 48213 }))

28. WebLLM + WebGPU + WASM 브라우저 추론
7644148517711188730

질문 — 브라우저에서 경량 LLM으로 요약 같은 로컬 추론을 구현해야 합니다. WebLLM·WebGPU·WASM 세 가지의 협업 원리를 설명하고, 추론 중 버벅임·VRAM 초과·모델 로딩 지연 세 문제를 어떻게 해결하나요?

지원자 답변 — "WASM이 빠르고, WebGPU가 GPU를 쓰고, WebLLM이 프레임워크." → 누가 무엇을 호출하는지, 세 문제 해결책에서 막힘.

정답

  1. 계층 구분 — "누가 무엇을 하는가"가 질문의 첫 관문.

    • WebLLM = 상위 오케스트레이션 계층. 모델 가중치 다운로드·캐싱, 토크나이저, KV 캐시 관리, 채팅 템플릿 적용, 샘플링(temperature/top-p), 스트리밍 출력 API를 담당합니다. 개발자가 직접 다루는 인터페이스
    • WebGPU = 실제 연산 실행 계층. 행렬 곱 등 텐서 연산을 컴퓨트 셰이더로 GPU에서 병렬 실행합니다. LLM 추론의 지배적 비용이 행렬 곱이므로 성능의 대부분이 여기서 결정됩니다
    • WASM = CPU 폴백 및 보조 계층. WebGPU를 지원하지 않는 환경의 폴백, 그리고 GPU 경로가 없는 연산(토크나이저, 일부 전/후처리)을 네이티브에 가까운 속도로 처리합니다
    • 호출 방향: 앱 코드 → WebLLM → (컴파일된 커널) → WebGPU 디바이스 → GPU. WASM은 WebGPU가 없을 때 대체 백엔드로, 또는 비연산 작업용으로 병행됩니다. "WASM이 WebGPU에 작업을 넘긴다"는 식의 설명은 부정확합니다 — 둘은 상·하 관계가 아니라 서로 다른 실행 백엔드입니다

  2. 버벅임(메인 스레드 점유) 해결.

    • Web Worker에서 추론 엔진을 실행합니다. WebLLM은 전용 워커 핸들러를 제공합니다. 메인 스레드는 UI만 담당하므로 생성 중에도 화면이 반응합니다. 이게 가장 중요한 단일 조치입니다
    • 토큰을 받는 즉시 setState를 호출하지 않고 일정 간격(또는 requestAnimationFrame)으로 모아서 렌더합니다. 초당 수십 토큰마다 리렌더하면 그 자체가 버벅임의 원인입니다
    • 워커 ↔ 메인 통신은 postMessage 비용이 있으므로 토큰 단위보다 작은 배치로 묶습니다

  3. VRAM(GPU 메모리) 초과 해결.

    • 양자화가 핵심입니다. FP16 대비 4비트 양자화(q4f16/q4f32)는 메모리를 1/4 수준으로 줄입니다. 모델 선택 단계에서 결정되는 사항
    • 모델 크기를 기기 능력에 맞춰 선택: navigator.gpu.requestAdapter()로 어댑터 한계(maxBufferSize, maxStorageBufferBindingSize)를 조회해 사전에 로드 가능 여부를 판단하고, 불가하면 더 작은 모델이나 서버 추론으로 폴백합니다
    • KV 캐시가 컨텍스트 길이에 비례해 증가합니다. 최대 컨텍스트를 제한하고 긴 대화는 요약·슬라이딩 윈도우로 잘라냅니다. OOM의 실제 원인이 가중치가 아니라 KV 캐시인 경우가 많습니다
    • 사용이 끝나면 엔진을 명시적으로 해제(unload())해 GPU 버퍼를 반환합니다. 모바일에서는 상주시키지 않는 편이 안전합니다

  4. 모델 로딩 지연 해결.

    • 영속 캐시가 핵심입니다. 수백 MB~수 GB를 매번 받으면 쓸 수 없습니다. Cache API 또는 OPFS(Origin Private File System) 에 저장해 두 번째 방문부터는 네트워크 요청 없이 시작합니다
    • 가중치를 샤드로 분할해 병렬·재개 가능하게 받습니다. 중단 시 받은 샤드부터 이어받기
    • 진행률 콜백으로 진행 상황을 반드시 표시합니다. 수백 MB 다운로드 중 피드백이 없으면 이탈합니다
    • 모델 파일은 불변이므로 immutable 장기 캐시 + CDN
    • 예측 가능한 경우 유휴 시간에 선로딩

  5. 설계 판단 — 면접에서 가점이 되는 부분. 브라우저 로컬 추론은 프라이버시(데이터가 기기를 떠나지 않음)와 서버 비용 절감이 이득이고, 비용은 초기 다운로드·기기 성능 의존성·모델 품질 제약입니다. 그래서 실무에서는 하이브리드가 보통입니다: 민감 데이터나 오프라인은 로컬, 품질이 중요한 작업은 서버 API, 그리고 기기 능력 탐지로 자동 라우팅. "무조건 로컬"이라고 답하면 판단력이 없다고 봅니다.

  6. 모니터링. 첫 토큰 지연(TTFT), 초당 토큰 수, 모델 로드 시간, OOM 발생률, 폴백 비율을 기기 등급별로 수집합니다.

29. AI 대화 스트리밍 렌더링 컴포넌트 설계
7646707397049863355

질문 — 브라우저용 AI 대화 스트리밍 컴포넌트를 설계하세요. 요구사항: 첫 응답 200ms 이내, 긴 텍스트에서 버벅임 없음, 끊기면 자동 재연결, 출력 XSS 방지.

지원자 답변 — "fetch로 SSE 받아서 state에 렌더링." → 메인 스레드 점유, 재연결 시 메시지 유실, XSS 방지에서 막힘.

정답

  1. 전송 방식 선택 — 근거를 말해야 합니다.

    • SSE(EventSource): 서버→클라이언트 단방향 스트림. 자동 재연결과 Last-Event-ID 재개가 프로토콜에 내장되어 있습니다. AI 응답 스트리밍에 가장 잘 맞습니다. 단 커스텀 헤더를 붙일 수 없어(인증 토큰) 쿠키나 쿼리 파라미터로 우회해야 합니다
    • fetch + ReadableStream: 헤더를 자유롭게 쓸 수 있고 POST 본문을 보낼 수 있어 실무에서 더 많이 쓰입니다. 대신 재연결과 재개를 직접 구현해야 합니다. OpenAI/Anthropic SDK가 쓰는 방식
    • WebSocket: 양방향이 필요할 때(음성, 실시간 협업). 단방향 텍스트에는 과합니다
    • 실무 권장: fetch 스트림 + 직접 구현한 재연결. 헤더 제약이 없고 POST로 긴 프롬프트를 보낼 수 있기 때문입니다

  2. 첫 응답 200ms — 무엇을 줄이는지 분해합니다. 200ms는 첫 토큰이 화면에 보이는 시점으로 정의해야 달성 가능한 목표입니다.

    • 요청 전: 컴포넌트 번들을 첫 화면에 포함(lazy로 빼면 모델 응답보다 로딩이 느립니다), preconnect로 API 도메인 연결 미리 수립
    • 서버: 스트리밍을 켜서 생성 완료를 기다리지 않습니다. 이게 가장 큰 요인. 프롬프트 캐싱 활용
    • 클라이언트: 요청 즉시 사용자 메시지와 타이핑 인디케이터를 낙관적으로 렌더해 체감 지연을 제거합니다
    • 로컬 추론이라면 모델을 미리 워밍업해 둡니다 (→ 28번)

  3. 긴 텍스트 버벅임 방지 — 핵심 병목은 "토큰마다 전체 재렌더".

    • 토큰 배칭: 받은 토큰을 버퍼에 모아 requestAnimationFrame에서 프레임당 1회만 상태를 갱신합니다. 토큰마다 setState하면 초당 수십 회 리렌더가 발생합니다
    • 마크다운 파싱을 매번 전체 다시 하지 않습니다. 스트리밍 중에는 마지막 블록만 재파싱하고, 앞서 확정된 블록은 메모이즈해 고정합니다. 전체 재파싱이 긴 응답에서 가장 큰 비용입니다
    • 메시지 리스트 가상화: 대화가 길어지면 과거 메시지는 화면 밖입니다. 가상 스크롤로 DOM을 제한하고, 메시지 수 상한을 두거나 오래된 것은 접습니다
    • 코드 블록 신택스 하이라이팅은 스트리밍이 끝난 뒤에 적용합니다. 미완성 코드를 매 토큰마다 하이라이팅하면 매우 비쌉니다
    • 자동 스크롤은 사용자가 위로 올렸으면 멈춥니다(스크롤 위치 추적). 이걸 안 하면 과거 내용을 읽을 수 없습니다

  4. 끊김 자동 재연결 — 메시지 유실 없이.

    • 서버가 각 이벤트에 증분 ID를 부여하고, 클라이언트는 마지막으로 받은 ID를 기억합니다. 재연결 시 그 ID를 보내 그 지점부터 이어받습니다. SSE는 Last-Event-ID 헤더로 표준화되어 있습니다
    • 지수 백오프 + 지터로 재시도합니다(1s, 2s, 4s... 상한). 지터가 없으면 서버 복구 시 모든 클라이언트가 동시에 몰립니다
    • navigator.onLine과 online 이벤트로 네트워크 복구를 감지해 즉시 재시도
    • 재개가 불가능한 서버라면 최소한 부분 응답을 보존하고 "이어서 생성" 버튼을 제공합니다. 조용히 사라지게 하지 않는 것이 중요
    • AbortController로 사용자 중단(Stop) 지원 — 그리고 중단 시 받은 부분은 유지합니다

  5. XSS 방지 — 반드시 짚어야 하는 부분. AI 출력은 신뢰할 수 없는 입력입니다. 프롬프트 인젝션으로 악성 마크다운/HTML을 유도할 수 있습니다.

    • 원시 출력을 innerHTML/dangerouslySetInnerHTML에 절대 넣지 않습니다
    • 마크다운을 렌더하려면 파서가 HTML을 허용하지 않도록 설정하고(marked의 sanitize 대신 별도 정화 사용), 결과를 DOMPurify 같은 검증된 라이브러리로 허용 목록 기반 정화합니다. 직접 정규식으로 태그를 걸러내는 시도는 실패합니다
    • 링크는 rel="noopener noreferrer" + 스킴 검증(javascript:, data: 차단)
    • 이미지 출처 제한, 임의 <iframe> 금지
    • CSP를 함께 적용합니다 (script-src에 unsafe-inline 금지). 정화를 우회하는 공격이 있어도 2차 방어선이 됩니다
    • 가장 안전한 선택은 마크다운을 HTML로 변환하지 않고 React 엘리먼트로 직접 매핑하는 렌더러(react-markdown + rehype 플러그인 허용 목록)입니다

  6. 접근성·UX 마무리. 스트리밍 중 aria-live="polite"로 스크린 리더에 전달(단 토큰마다 읽으면 안 되므로 문단 단위), 복사 버튼, 재생성, 에러 시 명확한 안내와 재시도.

30. AI가 생성한 React 코드를 어떻게 검증하나

질문 — 팀이 AI 보조 개발을 전면 도입했습니다. AI가 상태 관리·부수 효과·엔지니어링 래핑을 포함한 300줄 React 컴포넌트를 한 번에 생성하고, 코드가 매우 전문적으로 보입니다. 이 코드가 신뢰할 만한지, 바로 머지해도 되는지 어떻게 판단하나요?

지원자 답변 — "UI가 맞고 기능이 동작하면 씁니다" / "사람이 한 줄씩 봅니다." → 표준화된 검증 체계가 없음.

정답 — 핵심 통찰: "AI가 빠르게 생성한 코드"와 "운영에 올릴 수 있는 코드"는 다른 문제입니다. AI는 관례를 잘 따르기 때문에 표면이 깔끔하고 경계 조건이 비어 있는 패턴을 만듭니다. 그래서 "보기 좋은지"가 아니라 "무엇이 빠졌는지" 를 체계적으로 찾아야 합니다.

1층: 자동화로 거를 것 (사람이 볼 필요 없는 것)

  • TypeScript strict 모드 통과, any 금지
  • ESLint — 특히 react-hooks/exhaustive-deps와 react-hooks/rules-of-hooks를 에러로 설정. AI가 가장 자주 틀리는 영역입니다
  • 포매터, import 순서, 네이밍 규칙
  • 테스트 커버리지 임계값, 번들 크기 예산
  • 이 계층을 자동화하지 않으면 리뷰어가 사소한 것에 시간을 쓰고 중요한 것을 놓칩니다

2층: React 고유 함정 (AI가 통계적으로 자주 틀리는 지점)

  • useEffect 의존성 배열: 누락 → stale closure, 과다 → 무한 루프. 객체/배열을 의존성에 넣어 매 렌더 재실행되는 패턴
  • 정리(cleanup) 누락: setInterval, addEventListener, ResizeObserver, 구독, 진행 중 요청. 언마운트 후 setState 경고가 나는지 의도적으로 빠르게 마운트/언마운트해 확인합니다
  • useMemo/useCallback 오용: 의존성이 매 렌더 바뀌면 메모이제이션이 무의미하고 오버헤드만 남습니다. 반대로 꼭 필요한 곳에는 없는 경우
  • 조건부 훅 호출, 반복문 안의 훅
  • 키(key) 문제: 리스트에 index나 랜덤값 사용 (→ 6번)
  • 경쟁 상태(race condition): 요청 응답이 순서대로 오지 않을 때 늦게 온 구버전 응답이 최신 상태를 덮어씀. AbortController나 요청 ID 체크가 있는지
  • SSR 안전성: Next.js 환경에서 window/document/localStorage를 최상위에서 참조하면 서버에서 즉시 터집니다. AI가 매우 자주 하는 실수
  • 제어/비제어 컴포넌트 혼용, value 없이 onChange만 있는 입력

3층: 비즈니스 로직과 경계 조건 (AI가 알 수 없는 영역)

  • AI는 요구사항 문서의 암묵적 맥락을 모르므로 일반적인 템플릿을 채웁니다. 요구사항과 1:1로 대조해야 합니다
  • 빈 상태: 데이터 0건, null, 빈 배열
  • 에러 상태: API 실패 시 UI, 재시도 경로, 부분 실패
  • 로딩 상태: 중첩 로딩, 스켈레톤
  • 중복 실행: 버튼 연타, 폼 이중 제출 (→ 12번)
  • 약한 네트워크·타임아웃
  • 잘못된 입력·경계값: 음수, 초장문, 특수문자, 다국어
  • 응답 스키마 변경 방어: 서버 응답을 그대로 신뢰하고 data.items.map()을 호출하면 items가 없을 때 터집니다. 런타임 검증이나 옵셔널 체이닝이 있는지 (→ 24번)
  • 권한: AI는 역할을 모른 채 모든 버튼을 렌더합니다. 권한 분기가 누락되었는지 (→ 21번)
  • AI가 발명한 요구사항: 자동 저장, 확인 모달 같은 "있으면 좋을 것 같은" 기능을 임의로 추가하는 경우가 있습니다. 명세에 없는 동작은 제거 대상입니다

4층: 운영 리스크

  • 성능: 불필요한 리렌더, 큰 리스트의 가상화 부재, 매 렌더 새 함수/객체 생성
  • 보안: dangerouslySetInnerHTML, 링크 스킴 미검증, 민감 정보 로깅·노출
  • 에러 격리: 에러 바운더리가 있어 컴포넌트 하나가 전체를 무너뜨리지 않는지
  • 팀 공통 역량 누락: 국제화, 디자인 토큰 사용, 분석 이벤트, 스타일 격리, 접근성(라벨·포커스·키보드 조작) — AI가 가장 자주 빠뜨리는 범주입니다
  • 재사용성: 비즈니스 값이 하드코딩되어 겉보기엔 잘 추상화된 듯하지만 재사용 불가능한 경우

31. AI 시대 팀 코드 품질 관리
7686088690233894897

질문 — AI가 하루에 10여 개 페이지를 생성합니다. 스타일 통일성과 유지보수성을 어떻게 보장하고, 생성한 것을 바로 main에 머지해도 되나요? 엔지니어링 관리 체계를 설명하세요.

지원자 답변 — "ESLint와 Prettier로 포매팅 통일하면 됩니다." → 컴포넌트 네이밍 혼재, props 규약 불일치, 같은 기능의 서로 다른 구현이 여러 개 생기는 문제를 다루지 못함.

정답 — 30번이 "개별 코드를 검증"하는 문제라면, 이건 "속도가 올라간 상태에서 일관성을 유지" 하는 다른 문제입니다. 핵심 증상은 "각 페이지가 섬이 되는 것" — 돌아가지만 공통 추상화가 없어 유지보수 비용이 오히려 늘어납니다.

1층: 생성 전 — 제약을 주입한다 (가장 효과가 큰 지점)

  • AI의 문제는 "잘 못 쓰는 것"이 아니라 "규칙을 모르는 것" 입니다. 팀 규약을 구조화된 형태로 제공합니다
  • 프로젝트 규칙 파일(CLAUDE.md, .cursorrules 등)에 명시: 컴포넌트 작성 방식, 상태 관리 위치, API 호출 계층, 타입 선언 규칙, 금지 사항(DOM 직접 조작, 전역 상태 임의 생성)
  • 기존 코드를 참조 대상으로 지정합니다. "이 컴포넌트와 같은 패턴으로"가 추상적 규칙보다 훨씬 잘 작동합니다
  • 공용 컴포넌트/훅 라이브러리를 먼저 만들고 그것을 쓰게 합니다. 없으면 AI는 매번 새로 만듭니다 — 이게 "같은 기능의 구현이 여러 개" 문제의 직접 원인입니다
  • 타입을 먼저 정의하고(API 계약, props 인터페이스) 구현을 생성하게 하면 일관성이 크게 올라갑니다

2층: 생성 중 — 자동 게이트

  • 커밋·PR 단계에서 자동 검증: 타입 검사, ESLint(React Hooks 규칙 에러), 스타일린트, 테스트, 번들 크기
  • 커스텀 ESLint 규칙으로 팀 고유 규약을 강제합니다: 특정 디렉터리 외 전역 상태 선언 금지, 금지된 import 경로, 네이밍 컨벤션. 사람이 매번 리뷰에서 지적하는 항목은 규칙으로 승격합니다
  • 중복 코드 탐지(jscpd 등)로 "섬" 생성을 조기에 발견합니다
  • 로컬에서도 같은 게이트가 돌게(pre-commit 훅) 해서 CI 왕복을 줄입니다

3층: 생성 후 — 수렴시킨다

  • 주기적으로 생성된 코드에서 반복 패턴을 추출해 공용 라이브러리로 승격합니다. 이 단계를 생략하면 중복이 복리로 늘어납니다
  • 코드 리뷰의 초점을 이동: 문법·포매팅은 도구에 맡기고, 사람은 추상화 수준·결합도·재사용성·비즈니스 규칙을 봅니다
  • 고위험 영역(결제, 인증, 권한, 대용량 데이터)은 사람 리뷰 필수로 지정합니다
  • 반복 발견된 함정을 프롬프트 템플릿과 규칙 파일에 역류시켜 같은 실수가 두 번 나오지 않게 합니다

관점 — 면접에서 평가되는 지점

  • "AI를 코드 생산자로 쓰는 것"에서 "AI에 규칙을 부여하고 체계를 설계하는 것" 으로 역할이 옮겨집니다
  • 주니어는 AI를 타이핑 가속기로, 시니어는 표준화된 생산 설비로 씁니다
  • 속도가 올라갈수록 일관성 유지 비용이 병목이 되므로, 공용 추상화와 자동 게이트에 투자하는 것이 생산성의 실제 레버입니다
