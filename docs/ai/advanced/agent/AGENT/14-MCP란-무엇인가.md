# MCP란 무엇인가

> [← 전체 목차](../AGENT.md) · 이전: [JSON을 안정적으로 출력하는 법 — 4층 출력 방어선](13-JSON-안정-출력-4층-방어선.md) · 다음: [MCP와 A2A는 도대체 어떻게 선택하는가](15-MCP와-A2A-선택.md)

MCP의 핵심 본질은 **외부 데이터와 도구를 표준화된 방식으로 연결하는 것**이다. 모델 능력과 기업 데이터 자산을 어떻게 디커플링하고, 반복 작성되는 접착 코드를 없애며, 권한 통제를 서버 측으로 수렴시키는가.

MCP가 해결하는 것은 "외부 능력을 **하나의 통일된 표준으로** AI 애플리케이션에 노출할 수 있는가"다.

**MCP는 LLM 세계의 범용 연결 프로토콜이다.**

**MCP** 서버는 **후단 전체를 모델에 그대로 노출하는 것이 아니라**, 먼저 선언된 능력과 권한 규칙으로 필터링한다.

### **통제된 입구**

모델은 데이터베이스에 직접 접근하는 것이 아니라, **통제된 입구를 통해 허용된 리소스에만 접근한다.**

MCP의 엔지니어링 가치 = 세 가지를 **하나의 메커니즘**에 담는 것

- 리소스 접근
- 도구 호출
- 권한 경계

### **3대 적용 상황**

- 로컬 개발 — 프로젝트 구조, 코드 파일, 커밋 이력 읽기 — 서버가 선언한 능력 범위
- 사내 지식베이스 — 자료 조회 — "무엇을 조회할 수 있고 무엇을 조회할 수 없는지"를 MCP 서버가 통제
- 자동화 운영 — 서버 상태 조회, 나아가 통제된 조작 발동 — 표준 도구 + 통제된 조작

### **두 관점에서의 이득**

- **개발자 관점**: 같은 서버 능력을 여러 AI 애플리케이션이 재사용할 수 있으므로, 모델을 바꿀 때마다 접착 코드를 다시 쓸 필요가 없다
- **기업 관점**: 모델이 밑바탕 자산을 직접 건드리게 하지 않고, 접근 능력을 관리 가능한 서버 안에 포장한다

### 정리

MCP는 LLM 애플리케이션이 외부 데이터와 도구에 연결하기 위한 **표준화 프로토콜**이며, **호스트, 클라이언트, 서버**라는 구조를 통해 **모델 능력**과 **기업 데이터 자산을 디커플링**한다.

## **핵심 통찰**

1. **"기능 문제"를 "표준 문제"로 다시 진술하는 것이 이런 프로토콜 문제의 답변 템플릿이다** — "MCP가 무엇인가"를 물으면, 약한 답은 기능을 답하고(파일을 읽는다) 강한 답은 표준을 답한다(통일된 접속 프로토콜). 같은 재진술 기법이 REST, gRPC, OpenTelemetry 등 모든 "프로토콜류" 개념에 적용된다.
2. **접착 코드의 진짜 비용은 작성이 아니라 "곱셈"이다** — M개 모델 × N개 데이터소스 = M×N벌의 어댑터 코드. 표준 프로토콜을 도입하면 M+N이 된다. "상위 애플리케이션을 바꿀 때마다 배관을 다시 연결하는 것 같다"는 표현이 바로 이 곱셈 효과를 말한다.
3. **변하는 것과 변하지 않는 것의 분리가 디커플링의 판단 기준이다** — "업무 데이터도 안 변했고 권한 규칙도 안 변했는데 연결 코드는 고쳐야 한다"는 점이 반복 강조된다. 안정적인 것이 불안정한 것에 끌려 함께 바뀐다면 추상화 계층의 위치가 틀린 것이다.
4. **USB 비유가 성립하는 이유는 "프로토콜이 구현을 규정하지 않기" 때문이다** — USB는 어떤 마우스를 만들지 규정하지 않고, MCP도 데이터베이스 테이블을 어떻게 설계할지 규정하지 않는다. 비유로 답할 때는 이 층까지 짚어야지 "USB처럼 편리하다"에서 멈추면 안 된다.
5. **MCP의 보안 가치는 "서버가 능력을 선언하는 것"에서 오지 "모델의 자각"에서 오지 않는다** — 모델이 받는 것은 언제나 필터링된 표준 포맷 결과이며, 권한 판단은 모델이 데이터에 닿기 전에 발생한다. 이는 보안을 Prompt 계층에서 프로토콜 계층으로 내리는 것이다.
6. **한 번의 호출은 "능력 선언 → 권한 규칙 → 데이터 조회/필터링 → 표준 포맷 반환"이라는 4개 관문을 거친다** — 어느 하나가 빠지면 MCP는 평범한 HTTP 게이트웨이로 퇴화한다.
7. **서버는 재사용 가능한 자산이고 클라이언트는 교체 가능한 소비자다** — 이것이 투자 방향을 결정한다. 기업은 예산을 MCP 서버 구축에 써야지 AI 도구마다 맞춤 통합을 만드는 데 쓰면 안 된다.

## **엔지니어링 실전 Tips**

- MCP 서버 설계 시 **능력 선언(capabilities)은 Prompt가 아니라 서버에 써야 한다** — Prompt는 우회될 수 있지만 서버 선언은 그럴 수 없다.
- "후단 전체를 모델에 그대로 노출하지 말 것"은 실행 가능한 레드라인이다. 서버는 **필터링된** 결과 집합만 반환해야지 테이블 전체나 디렉터리 전체를 모델에 던지면 안 된다.
- 사내 지식베이스 상황에서는 서버 측에서 **행 단위 / 문서 단위 권한**을 걸어야 한다. 그렇지 않으면 "직원이 어떤 자료를 조회할 수 있는지"에 대한 통제가 Embedding 필터링으로 퇴화해 감사가 불가능해진다.
- 자동화 운영 상황에서는 "조회류 도구"와 "통제된 조작 발동류 도구"를 구분하고, 후자에는 반드시 독립된 인가와 감사 경로를 둘 것.
- MCP 도입 가치를 평가하는 간단한 기준: **상위 AI 애플리케이션이 몇 세트인가 × 내부 데이터소스가 몇 세트인가.** 둘 다 1보다 크면 MCP는 즉시 본전을 뽑는다.
- 마이그레이션 경로 제안: 기존 접착 코드를 먼저 "리소스"와 "도구" 두 종류로 쪼갠 다음 MCP 서버로 감쌀 것. 처음부터 전체 통합을 다시 쓰려 하지 말 것.
